## 1. 今の仕組み (コードで確かめたこと)

| 項目 | 今 | どこ |
|---|---|---|
| コード | プラグインのコードは**全部 `RM_Engine.exe` に静的リンク**。一覧は `plugins/BuiltinPlugins.cpp` (エディター) と `plugins/RuntimePlugins.cpp` (ゲームにも入る部分) の 2 つだけ | `plugins/*.cpp` |
| 「入っている」とは | exe の横の `Plugins/<作者>/<名前>/` (エンジンが持つ写し) を `%LOCALAPPDATA%\RM_Engine\Engines\<エンジン>\Plugins\<作者>\<名前>\` へ**フォルダごと写す**だけ。入っていないプラグインは、コードは exe にあるが初期化されない | `editor/plugin/Plugins.h` (`Install` / `CopyIn`) |

| `<エンジン>` | 版ではなく exe のフォルダで分ける (`EngineKey`: フォルダ名 + フルパスのハッシュ) | `editor/app/EngineKey.h` |

| 壊れた物を見つける | ビルドが `RM_Engine.files.json` (exe・`Lang/**`・`Plugins/**` の大きさと SHA-256) を書き、Hub の「確認する」で比べる。**署名は無い** (改ざんは防げない) | `editor/app/Integrity.*`・`tools/make_filelist.ps1`・`platform::Sha256File` (BCrypt) |
| エンジンの版 | `kEngineVersion = "0.0.1"` | `src/base/Version.h` |
| 自動アップデート | オプションに「エディターの自動アップデート」があるが**設定だけ** (取ってくる先が決まっていない) | `editor/project/Options.h`・ARCHITECTURE の「自動アップデート」 |
| C のランタイム | エンジンは **`/MT`** (Debug は `/MTd`)。切り替えは `src/RM.Common.props` の `RmCrt` の 1 か所 | `RM.Common.props` |
| DLL の前例 | ゲームのスクリプトは DLL。境目は **C だけ** (`RmModuleInit(const RmApi*, uint32_t abi)` の 1 本、版を両側で確かめる、`std::string` を渡さない、DLL の物は DLL の関数で作る・壊す)。スクリプトの DLL は `/MD` でエンジンは `/MT` でも動く | `game_production/runtime/sdk/RmAbi.h`・ARCHITECTURE のスクリプトの節 |
| プラグイン同士の受け渡し | `RuntimeRegistry::Contribute(口, static な物)` と `Contributions<T>(口)`。**C++ の型と `typeid` で見分ける** | `core/RuntimeRegistry.h` |

つまり、今のままで「落として入れる」ことができるのは、**エンジンがもう持っている (exe に入っている) プラグインのファイルを新しくすること**だけ。新しいコードは届けられない。

## 2. 目標と範囲

- **目標**: Hub の「プラグイン」から、エンジンに付いていないプラグインを**ダウンロードして入れる**・新しい版に**更新する**。
- **最初は公式 (`rm_engine`) だけ**。ほかの作者のプラグインは、安全の仕組み (§7 の署名) ができてから。
- **GitHub の有料の機能は使わない** (ユーザーの決まり)。GitHub Actions は動かさない。配るファイルは**手元でビルドして**上げる。
- **配る場所はユーザーのポートフォリオ** https://ir-cola.github.io/ (GitHub Pages) **に作る専用のページ** (2026-11-21 の決定)。`index.json` と zip をそのサイトに置き、Hub はそこを読む。GitHub Pages は公開のサイトなら無料。ただし 1 ファイル 100 MB まで・サイト全体でおよそ 1 GB・転送量の目安は月 100 GB なので、大きい zip が増えたら、zip だけをサイトのリポジトリの Releases に置き、`index.json` からそこを指す (どちらも無料)。
- **将来は、エンジン本体はプラグインを 1 つも持たずに配る**。公式プラグインも全部、ダウンロードして入れる (2026-11-21 の決定)。**今はまだ外さない** (静的リンクのまま。DLL にできてから外す)。
- エンジン本体の自動アップデートも、同じ一覧と同じ道で行う (段階 3)。

範囲の外 (今回は作らない): プラグインのストアの画面 (評価・検索など)、有料のプラグイン、ほかの作者の登録の受付。

## 3. 配る形

### 3-1. パッケージ 1 つ = プラグイン 1 つ

ファイル名: `<作者>.<名前>-<版>.zip` (例 `rm_engine.weather-0.2.0.zip`)。中身は今の `Plugins/<作者>/<名前>/` と同じ並び:

```
plugin.json
lang/en.json
themes/*.json            (あれば)
templates/<id>/...       (あれば)
bin/<作者>.<名前>.dll    (段階 2 から。コードのあるプラグインだけ)
```

### 3-2. plugin.json に足すキー (案)

| キー | 例 | 意味 |
|---|---|---|
| `version` | `"0.2.0"` | プラグインの版 (数 3 つ。大きいほど新しい) |
| `engine` | `{ "min": "0.0.5" }` | 動くエンジンの一番古い版 (Godot の `compatibility_minimum` と同じ。境目は足すだけなので、上の限りは書かない。§6 段階 2) |
| `code` | `false` | コードがあるか (無いもの = テーマ・テンプレートだけ) |

知らないキーは今の `ParsePluginManifest` が読み飛ばすので、前のエンジンでも読める (憲法 6)。

### 3-3. zip にするか、自分の形にするか

エンジンには zip の展開が無い。案は 2 つ:

| 案 | よい所 | 気になる所 |
|---|---|---|
| A. zip (miniz などの小さな展開のライブラリを `src/third_party` に足す) | ふつうのツールで作れる・中を見られる | ライブラリが 1 つ増える (TECHNOLOGIES.md に書く) |
| B. 自分の形 (`.rmpkg`: 先頭に JSON の目次、続けてファイル。圧縮なし) | 依存が増えない。書き出しの `Game.rmpak` と同じ考え方 | 作る道具 (`tools/make_plugin_package.ps1`) も自分で書く |

おすすめは **A (zip)**。人に渡したり中を確かめたりしやすいため。

## 4. 一覧 `index.json`

Hub が最初に読む 1 つのファイル。どのプラグインのどの版があり、どこから落とし、ハッシュは何かを書く。

```json
{
  "kind": "rm_engine.plugin_index",
  "formatVersion": 1,
  "updated": "2026-11-21",
  "plugins": [
    {
      "author": "rm_engine",
      "name": "theme_paper",
      "displayName": "紙",
      "versions": [
        {
          "version": "0.1.0",
          "engine": { "min": "0.0.1" },
          "code": false,
          "url": "https://ir-cola.github.io/rm_engine/plugins/rm_engine.theme_paper-0.1.0.zip",
          "size": 12345,
          "sha256": "…小文字の 16 進…",
          "requires": [ { "author": "rm_engine", "name": "game_production" } ]
        }
      ]
    }
  ],
  "engine": {
    "version": "0.0.2",
    "url": "…", "size": 0, "sha256": "…"
  }
}
```

- 置き場所: ポートフォリオ https://ir-cola.github.io/ の専用のページの下 (2026-11-21 の決定。パスは例: `https://ir-cola.github.io/rm_engine/index.json`、ページを作るときに決める)。URL はエンジンに 1 か所だけ書く (憲法 2)。
- 各 zip も同じサイトの下 (例: `.../rm_engine/plugins/<作者>.<名前>-<版>.zip`)。大きい zip は、サイトのリポジトリの Releases に置いて `url` でそこを指してもよい (§2)。
- 上げ方 (手元): ビルド → `tools/make_plugin_package.ps1` で zip と `index.json` を作る → サイトのリポジトリに入れてプッシュ (GitHub Pages が出す)。**自分で Actions を書かない** (ポートフォリオは今も GitHub Pages で出ている。Pages の「ブランチから出す」公開は GitHub が裏で動かす仕組みで、公開リポジトリなら無料)。
- `requires` は zip の `plugin.json` と同じ。入れる前に前提を計画するため (今の `InstallPlan` と同じ考え) に、落とす前から分かるよう一覧にも写す。

## 5. ダウンロードと確認の流れ

```
Hub「プラグイン」を開く / 「更新を確かめる」
  1 index.json を落とす (WinHTTP。作業スレッド editor/app/Worker で)
  2 読む (純粋: ParsePluginIndex)。このエンジンの版で動く物だけ残す (純粋: 版の比べ)
  3 一覧に「入れる」「更新 (新しい版あり)」を出す
「入れる」を押す
  4 前提も含めて何を落とすか決める (今の InstallPlan に「落とせる物」を足す)
  5 zip を %LOCALAPPDATA%\RM_Engine\Downloads\ に落とす (.part に書いて、終わったら名前を変える)
  6 大きさと SHA-256 を一覧と比べる (platform::Sha256File)。違えば捨てて「壊れていました」
  7 中のパスを確かめる (§7)。<名前>.installing に展開
  8 今の CopyIn と同じ手順で置く (.old へよける → 置く → 消す。だめなら戻す)
  9 Reload (エディターが開いていないとき。今の ApplyEngineRefresh と同じ決まり)
```

- **失敗したら前のまま**: 6〜8 のどこで止まっても、入っていた版はそのまま動く。
- **オフラインでも動く**: 一覧が落とせないときは「確かめられませんでした」と出すだけ。入っている物は今までどおり使える。最後に読めた `index.json` を写しておき、一覧の表示に使う。
- 通信: **WinHTTP** (Windows に入っている。HTTPS とリダイレクト (GitHub の資産は別の場所へ飛ぶ) を扱える)。プロキシは Windows の設定に従う。
- 落とした物は「エンジンの写し」ではなく「入れた物」として扱う。エンジンを更新したときの写し直し (`PlanEngineRefresh`) で、**落とした新しい版をエンジンの古い写しで上書きしない**ように、どこから来たか (`source: "engine" | "download"`) と版を `<入れた先>` に残す。
- **後で署名**: 一覧 `index.json` に署名を付け (Ed25519 など。公開鍵をエンジンに埋める)、署名が合わない一覧は使わない。ハッシュだけでは「GitHub のアカウントを乗っ取られた」ときに守れないため。

## 6. 段階

### 段階 1: コードの無いプラグインを落とす (テーマ・テンプレート)

- コードを読み込まないので、§1 の C++ の問題が無い。**最初に作るのはここ**。
- 要る変更: Hub の一覧の 1 行を「exe に組み込まれたプラグイン」から「exe に組み込まれたもの + `code: false` の入れたもの」に広げる (`Plugins::Load` / `ResolvePlugins`)。テーマ (`themes/*.json`) とテンプレート (`templates/`) は今もファイルから読んでいるので、そのまま効く。
- 作るもの: WinHTTP の取得 (`platform` に)、zip の展開、`index.json` の読み、Hub の「入れる / 更新」の行、`tools/make_plugin_package.ps1`。

### 段階 2: コードのあるプラグインを DLL にする — 方式 B (Godot 式) に決めた

**2026-11-21 の決定: Godot の GDExtension と同じ「C の境目 + C++ の包み」にする。**

今のプラグインは C++ の型 (`std::string`・`std::vector`・`typeid`・仮想関数) をそのまま渡し合っている。C++ の型の中身の並びはコンパイラーと設定で変わるので、そのまま DLL にすると、エンジンと同じ版・同じ設定でビルドした物しか読めない (方式 A。Unreal Engine はこの形で、エンジンの版ごとにプラグインを作り直す)。エンジンにプラグインを付けず全部を落として使う (§2) うえ、版を細かく上げていく (§8) ので、A では版を上げるたびに全部の配り直しになる。だから B にする。

| 参考 | やり方 |
|---|---|
| Godot (GDExtension) | エンジンとの間は C だけ (`gdextension_interface.h`)。関数は**名前で取りに行く** (`get_proc_address`)。その上の C++ の包み `godot-cpp` で、作者は普通の C++ で書く。説明ファイルに動く一番古い版 (`compatibility_minimum`) |
| Unity (ネイティブのプラグイン) | `extern "C"` の関数と、GUID 付きの C の構造体の表 (`IUnityInterfaces` / `IUnityGraphics`) を名前で取りに行く。表に版がある |
| Unreal Engine | C++ のモジュールをエンジンの版ごとにビルドし直す (方式 A) |
| このエンジンのスクリプト | もう C の境目 (`RmAbi.h`: `RmModuleInit` の 1 本・関数の表・`RmFieldDesc` などの素の構造体) と C++ の包み (`RM.h`・`RM3D.h`)。ただし ABI の版が変わると前の DLL は読まない (作り直す前提)。プラグインはそこを変える (下の 2) |

**境目の決まり (案)**

1. **入口は 1 本**: DLL が出すのは `RmPluginEntry(getProc, plugin, &init)` だけ。エンジンは `plugin.json` の版を確かめてから `LoadLibrary` → `GetProcAddress("RmPluginEntry")`。
2. **エンジンの機能は名前で取りに行く** (`getProc("rm.core.log_info")` → 関数ポインター)。足すときは新しい名前を足すだけ。**消さない・引数を変えない** (変えたいときは `..._2` を足す)。だから古いプラグインは新しいエンジンでもそのまま動く。プラグインは自分が使う名前を最初に全部取り、1 つでも無ければ「エンジンが古い」と理由を出して読まない (`plugin.json` の `engine.min` と二重に守る)。
3. **構造体は先頭に自分の大きさ** (`uint32_t size`)。後ろに足すだけで、読む側は大きさを見て、知らない後ろの欄は既定値として扱う。
4. **初期化の段** (Godot の initialization level と同じ): `Core` (数学・ログ) → `Runtime` (部品・システム・サービス: ゲームにも入る) → `Editor` (インスペクター・シーンビュー・パネル・ソフト)。終わるときは逆の順。書き出したゲームは `Runtime` までしか呼ばない (憲法 4 の柵がそのまま境目の段になる)。
5. **データの型は今の反映の形で渡す**: 部品やシステムの型は、スクリプトと同じ `RmFieldDesc` / `RmStructDesc` / `RmEnumDesc` の表で登録する (rmgen がプラグイン用にも表を書く)。保存・読み込み・インスペクター・Undo は今の道をそのまま通る (憲法 1・9)。
6. **メモリは確保した側が解放する**: 文字列は呼び出しの間だけ生きる UTF-8 の `const char*`。返す文字列は呼び出し側の入れ物 (関数) に書いてもらう。だからエンジンは `/MT` のままでよく、DLL は `/MD` で自分の C ランタイムを持てる。
7. **口 (Contribute) も表で**: 今の `registry.Contribute(口, static な物)` は、口ごとに C の構造体 (先頭に大きさ) を決めて渡す。口の名前は今のまま。プラグインどうしは、相手が出す C の表を名前で取る (`getApi("rm_engine.physics.api", 1)`)。今のスクリプトの `ScriptApiPart{名前, 版, 表}` と同じ形。
8. **COM はそのまま越えてよい**: `ID3D11Device*` などの COM のインターフェースは、作りが C の表 (vtable) で決まっていて変わらないので、描画するプラグインにはそのまま渡す (Unity の `IUnityGraphicsD3D11` と同じ)。
9. **C++ の包み** (`godot-cpp` にあたる物、`sdk/` にヘッダーだけ): 作者は `class MyComponent`・`RM_PROPERTY`・`rm::Entity` のような普通の C++ で書き、包みが C の表を呼ぶ。今のスクリプトの SDK (`RM.h`) と同じ書き味にそろえる。

**出していく順 (案)**: 一度に全部ではなく、プラグインの種類ごとに表を足していく。

| 順 | 表に出す物 | これで DLL にできる公式プラグインの例 |
|---|---|---|
| 1 | ログ・数学・反映の型の登録・部品・システム・Play 中のサービス | ランタイムだけの小さな物 (まず試しの 1 つ) |
| 2 | インスペクターの見せ方・シーンビューの線・作った物の口 | 物理・ゲーム UI の一部 |
| 3 | 描画 (3D 空間の口・COM の D3D11) | 天候・パーティクル |
| 4 | エディターの画面 (`w::` の部品・ソフト・パネル) | ゲーム制作そのもの・3D / 2D のシーンビュー |

公式プラグインを全部 DLL にできたら、エンジンから静的リンクを外す (§2)。

方式のほかに決めること:

- **静的リンクと共存 (移る間だけ)**: 最後は全部の公式プラグインを DLL にしてエンジンから外す (§2)。移る間は、まだ静的リンクの物と DLL の物が混ざる。同じ ID が両方にあるときは**版の新しい方**を使い、DLL が読めなければ静的リンクの方に戻る。
- **層の柵**: `layers.txt` と `check_layers.ps1` は今のまま効く (ソースの `#include` を見るので、DLL にしても同じ柵)。DLL のプロジェクトを作る道具が `requires` に無いプラグインのヘッダーを読めないようにする (include のフォルダを前提だけにする)。
- **書き出したゲーム**: 今は `runtime/` の `.lib` をリンクする。落としたプラグインのゲームの部分も同じように `.lib` で配るか (GameKit に足す)、ゲームの横に DLL を置くかを決める。
- **読むのは Hub にいる間だけ**: 今もエディターが開いている間はプラグインを読み直さない。DLL の `FreeLibrary` も同じ決まりにする。

### 段階 3: エンジン本体の自動アップデート

- 同じ `index.json` の `engine` の欄に新しい版の zip と SHA-256 を書く。
- 動いている exe は自分を上書きできないので、**小さな更新の exe** (または次の起動のとき) に入れ替えを任せる。入れ替えに失敗したら前の版で起動する。
- オプションの「エディターの自動アップデート」をここで効かせる。

## 7. 安全

| 心配 | 守り方 |
|---|---|
| 落としたファイルが壊れている・途中で切れた | 一覧の大きさと SHA-256 と比べる。違えば捨てる |
| 一覧そのものを書き換えられる | 段階 1 は HTTPS + GitHub を信じる。**後で一覧に署名** (公開鍵をエンジンに埋める) |
| zip の中のパスで外のフォルダに書く (`../`・`C:\`・`\\server\`) | 展開の前に全部のパスを確かめ、1 つでもだめなら全部断る (純粋: `ZipPathProblem`)。`..`・絶対パス・ドライブ名・`:`・Windows の予約名・大きすぎる数・合計の大きさの上限 |
| DLL は PC の上で何でもできる | 最初は**公式だけ** (一覧の作者が `rm_engine` の物だけ読む)。ほかの作者を入れるときは、入れる前に「このプラグインはパソコンの全部にさわれます」とはっきり聞く。署名が無い物は入れない |
| ユーザーのファイルを消す | 落とした物を置くのはプラグインのフォルダだけ。プロジェクトのフォルダには何も書かない |

## 9. テストの方針 (憲法 5: 純粋な計算は I/O から離してテスト)

| 純粋な部分 | 確かめること |
|---|---|
| `ParsePluginIndex` | 正しい一覧を読む・知らないキーは捨てずに持つ・欄が足りない / 型が違う物は理由付きで飛ばす・新しい `formatVersion` は読まない |
| 版の比べ (`CompareVersion`・`EngineFits`) | `0.10.0` > `0.9.0`・`min` の境目・書き方が違う版は「合わない」 |
| `ZipPathProblem` | `../a`・`a/../../b`・`C:/x`・`\\server\x`・`con.txt`・空の名前を断る。ふつうのパスは通す |
| ハッシュの比べ | 大文字と小文字の 16 進を同じに扱う・長さが違えば違う |
| 入れる計画 (`InstallPlan` の拡張) | 落とす物と、エンジンにある物の混ざった前提・つなぎが一緒に来る・堂々巡り |
| 写し直しとの関係 | 落とした新しい版を、エンジンの古い写しで上書きしない |

通信 (WinHTTP) と展開とファイルの置き換えは薄い殻にして、殻の中では判断をしない。殻はローカルの小さな HTTP サーバーか、ファイルの URL で試す。

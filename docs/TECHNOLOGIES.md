# 使っている技術のメモ

RM Engine で使っている技術と、これから使う予定の技術をまとめる。人に説明できるようにするためのメモ。
**機能を足して新しい技術を使ったら、ここに書き足す** (一番下の「追記の記録」にも 1 行足す)。

1 つの技術は次の形で書く。

- **何か** — その技術の一言の説明
- **何に使っているか** — RM Engine の中での役目
- **なぜそれか** — 選んだ理由 (ほかの選択肢と比べて)
- **どこ** — コードの場所

---

## 1. 全体の形

RM Engine は「ゲーム・イラスト・作曲・3D モデルなどを、プラグインを足して 1 つのソフトで作る」ための制作環境。
Windows のデスクトップアプリで、C++ で一から書いている (既製のゲームエンジンや UI ライブラリは使っていない)。

```
src/base      L0  文字列・JSON・ログ (Windows も知らない純粋な部品)
src/core      L2  Undo・リフレクション・プラグインの ID
src/platform  L3  Windows: ウィンドウ・GPU・ファイル・ダイアログ
src/ui        L4  UI の土台 (入力・文字の編集・描画の受け口)。色は持たない
src/editor    L6  Hub・エディターの枠・パネル・インスペクター・階層 (ゲームには入らない)
plugins/            ソフトはプラグインで足す (いまは「ゲーム制作」)
```

- 番号の小さい層は大きい層を知らない (下から上へだけ依存する)。こうすると、ゲームに入れる部分 (L0〜L4) からエディターを切り離せる
- この決まりは `layers.txt` に書き、`tools/check_layers.ps1` がビルドのたびに `#include` を全部調べて破っていないか確かめる (4-3)

## 2. 言語と開発環境

### C++20
- **何か** — C++ の 2020 年版の規格
- **何に使っているか** — エンジン全部
- **なぜそれか** — 描画やファイルを細かく速く扱える。C++20 の `std::format` (文字の組み立て)・`std::span` (配列の一部を渡す)・`consteval` (コンパイル時の検査)・`requires` (型の条件)・`<=>` / `= default` の比較 を使っている
- **どこ** — 全部。例: プラグイン ID をコンパイル時に検査する `consteval PluginIdLiteral` (`src/core/PluginId.h`)

### Visual Studio 2022 / MSBuild
- **何か** — Microsoft の開発環境と、そのビルドの仕組み
- **何に使っているか** — ビルド (`RM_Engine.sln` と各 `.vcxproj`)。共通の設定は `src/RM.Common.props` に 1 か所
- **なぜそれか** — 対象が Windows だけなので、Windows の機能とデバッガーを一番うまく使える (ユーザーの決定)
- **設定** — `/W4` (警告を多めに出す) で警告 0 を保つ / `/utf-8` (ソースは UTF-8) / 静的 CRT (配るときに追加のランタイムが要らない) / x64

### Git と GitHub Actions (CI)
- **何か** — 変更の記録 (Git) と、プッシュのたびに自動でビルドする仕組み (CI)
- **何に使っているか** — https://github.com/ir-cola/RMEngine (非公開)。プッシュすると Windows のマシンで Debug と Release をビルドし、テストと層の検査まで通るか確かめる
- **どこ** — `.github/workflows/ci.yml`、`tools/build.ps1`

### PowerShell
- **何に使っているか** — ビルドの手順 (`tools/build.ps1`: ビルド → テスト → 層の検査)、層の検査 (`tools/check_layers.ps1`)、アイコンとロゴの作成 (`tools/make_resources.ps1`: .NET の System.Drawing で PNG から .ico を作る)
- **なぜそれか** — Windows に最初から入っていて、追加のツールが要らない

## 3. Windows と描画

### Win32 API (ウィンドウとメッセージ)
- **何か** — Windows のアプリの一番下の仕組み。ウィンドウは「メッセージ」(マウスが動いた・キーが押された・描き直して など) を受け取って動く
- **何に使っているか** — Hub・エディター・外に出したパネルのウィンドウ。マウス (`WM_LBUTTONDOWN` …)・キー (`WM_KEYDOWN`)・文字 (`WM_CHAR`)・大きさ (`WM_SIZE`)・DPI の変化 (`WM_DPICHANGED`)。ドラッグ中はマウスを捕まえる (`SetCapture`)
- **なぜそれか** — 余計な層が無く、何が起きているか全部見える。Windows だけが対象なので、間に別のライブラリを挟む理由が無い
- **どこ** — `src/platform/Window.*`、`src/editor/app/ScreenWindow.*`

### Per-Monitor DPI v2 と DIP
- **何か** — 画面の細かさ (DPI) がモニターごとに違っても、正しい大きさで描くための仕組み。DIP = 「96 DPI のときの 1 ピクセル」を単位にした長さ
- **何に使っているか** — UI は全部 DIP で考え、描くときだけ実際のピクセルに直す。モニターを移ると `WM_DPICHANGED` で描き直す
- **どこ** — `resources/app.manifest` (`PerMonitorV2`)、`GetDpiForWindow`

### Direct3D 11 + DXGI
- **何か** — GPU を使う Windows の描画の仕組み (D3D11) と、画面へ出す仕組み (DXGI のスワップチェーン)
- **何に使っているか** — いまは Direct2D の土台。これからシーンビューや 3D の描画もここに乗る
- **なぜそれか** — Windows ならどの PC でも動き、情報も多い。D3D12 より書く量が少ない
- **どこ** — `src/platform/Gfx.*`

### Direct2D / DirectWrite
- **何か** — GPU で 2D の図形 (Direct2D) と文字 (DirectWrite) を描く Windows の仕組み
- **何に使っているか** — エディターの UI 全部 (四角・角丸・線・文字・画像)。日本語の文字、文字の幅の計測、はみ出したときの「…」、折り返しも DirectWrite
- **なぜそれか** — きれいな文字 (ClearType・日本語) をすぐに出せる。D3D11 と同じ GPU の上で動く
- **どこ** — `src/ui/Painter.*` (描く命令の受け口)、`src/platform/Gfx.*`

### WIC (Windows Imaging Component)
- **何か** — Windows に入っている画像の読み込みの仕組み (PNG・JPEG・BMP …)
- **何に使っているか** — Hub のロゴ (exe に埋め込んだ PNG) の読み込み。これからアセットの画像にも使う
- **なぜそれか** — Windows に最初から入っていて、配るものが増えない
- **どこ** — `src/platform/Gfx.cpp` (`LoadBitmapFromMemory`)

### IME (IMM32)
- **何か** — 日本語入力 (かな漢字変換) を受け取る Windows の仕組み
- **何に使っているか** — 入力欄で日本語を打てるようにする。変換中の文字 (下線付き) と確定した文字を受け取り、候補の窓を入力欄のカーソルの位置に出す
- **どこ** — `src/editor/app/ScreenWindow.cpp` (`WM_IME_COMPOSITION` など)、`src/ui/TextEdit.*`

### DWM (デスクトップ ウィンドウ マネージャー)
- **何に使っているか** — タイトルバーを暗い色にする (`DWMWA_USE_IMMERSIVE_DARK_MODE` / `DWMWA_CAPTION_COLOR`)、ウィンドウの見えている本当の四角を知る (`DWMWA_EXTENDED_FRAME_BOUNDS`。ドッキングでマウスの下のウィンドウを探すとき)
- **どこ** — `src/platform/Window.cpp`、`src/platform/Shell.cpp`

### シェルと COM
- **何か** — COM は Windows の部品を呼び出す仕組み。シェルはエクスプローラーまわりの機能
- **何に使っているか** — 「開く」「フォルダを選ぶ」のダイアログ (`IFileOpenDialog`)、エクスプローラーでファイルを選んだ状態で開く (`SHOpenFolderAndSelectItems`)、ドキュメントや AppData の場所 (`SHGetKnownFolderPath`)
- **どこ** — `src/platform/Shell.*`

### ファイルの安全な書き方
- **何か** — まず `<ファイル>.tmp` に書いてディスクまで書き切り (`FlushFileBuffers`)、それから置き換える (`MoveFileEx`)
- **なぜそれか** — 保存の途中で落ちても、半端なファイルが残らない (前の版か新しい版のどちらかが必ず残る)
- **どこ** — `platform::WriteFileAtomic` (`src/platform/Shell.cpp`)

### 文字コード: UTF-8 と UTF-16
- **何に使っているか** — データの文字は UTF-8 の `std::string`。Windows と DirectWrite に渡すときだけ UTF-16 (`std::wstring`) に変える
- **なぜそれか** — ファイル (JSON) と相性がよく、変える場所を 1 か所 (`base/Utf.h`) に決めておけば文字化けの原因を探しやすい。manifest で exe の文字コードも UTF-8 にしている

## 4. UI の作り方

### 自作の即時モード UI (ImGui は使わない)
- **何か** — 「即時モード」= 毎回の描画で「ボタンをここに描く。押されたら true」とコードで書く UI の作り方。部品の状態をあらかじめ組み立てて持っておく (保持モード) のではなく、毎回描くコードがそのまま UI になる
- **何に使っているか** — Hub とエディターの画面全部
- **なぜそれか** — 書く量が少なく、データと画面がずれない。ImGui (有名な即時モード UI) は使わないとユーザーが決めたので、土台から自作した
- **工夫**
  - 何も起きていないときは描かない (入力・大きさの変化・タイマーがあったときだけ描く) → CPU を使わない
  - 部品は文字列の ID (ハッシュ) で見分ける。前のエンジンでは番号で見分けていて、番号がぶつかる不具合があった
  - 土台 (`src/ui`) は色を持たない。見た目 (`src/editor/widgets` の Theme) と分けたので、ゲームの UI を同じ土台で作っても、エディターの色が混ざらない
  - メニューや一覧はフレームの最後に描く (オーバーレイ)。パネルの端で切れない
- **どこ** — `src/ui/Context.*`、`src/editor/widgets/*`

### 部品の集まり (ImGui のように使い回す)
- **何か** — ボタン・行・タブ・見出し・印・箱を 1 つずつ関数にしたもの。画面のコードは「ここにボタン」と呼ぶだけで、押されたかどうかが返る (ImGui と同じ使い方。ImGui そのものは使わない)
- **なぜそれか** — 前は画面ごとに四角を塗っていて、見た目を変えるには全部の画面を直す必要があった。部品に集めると、1 か所直せば全部変わる
- **どこ** — `src/editor/widgets/Widgets.*`

### グラデーションと影 (Direct2D)
- **何か** — 単色の四角を、上が少し明るく下が少し暗い**縦のグラデーション**にして、光が上から当たっているように見せる。色は元のパレットの色を白や黒に少し混ぜて作るので、色合いは変わらない (`Shade` = 白か黒へ何割か寄せる計算)
- **どう作ったか** — Direct2D の `ID2D1LinearGradientBrush`。色の組ごとにブラシを 1 つ作って覚えておき、描く四角に合わせて始点と終点だけ動かす (毎回作ると遅い)
- **影** — 本物のぼかし (ガウスぼかし) は重いので、少しずつ広く薄くした角丸を 4 枚重ねて、ぼけた影に見せている
- **印** — ×・⋯・▾ などを文字 (フォント) ではなく線と点で描く。文字だと位置がフォント次第でずれる (「…」が下に寄る) が、線ならいつも真ん中
- **どこ** — `src/ui/Painter.cpp` (`FillRoundRectGradient` / `Shadow`)、`src/editor/widgets/Theme.h` (`Raised` / `Gentle` / `Sunken` / `AccentOf`)

### 角ごとに丸さの違う四角と、色が変わる線 (パスジオメトリ)
- **何か** — くっついたパネルの角は四角、外側の角だけ丸くするため、**角ごとに半径の違う四角**を描く。Direct2D の角丸は 4 つの角が同じ丸さしか描けないので、形を自分で組み立てる
- **どう作ったか** — `ID2D1PathGeometry` (パス = 線と弧をつないだ形)。辺は直線 (`AddLine`)、丸い角は 4 分の 1 の円弧 (`AddArc`)、半径 0 の角は弧を飛ばすだけ。できた形を塗る (`FillGeometry`) か、線で縁取る (`DrawGeometry`)
- **縁の線** — 外側の暗い線はパネルの 1 ドット外に引く。パネルのあいだを 1 ドットあけると、両側のパネルの外側の線が同じ所に重なって、区切りがちょうど 1 本になる。内側の明るい線はグラデーションのブラシで引くので、上が明るく下が薄い
- **どこ** — `src/ui/Painter.cpp` (`RoundRectPath` / `FillRoundRectGradient(Corners)` / `StrokeRoundRectGradient`)、`src/editor/widgets/Widgets.cpp` (`DrawPanelFrame`)、`src/editor/dock/DockSpace.cpp` (どの角が外側かを決める)

### 線と曲線で形を描く (ベジェ曲線と回転)
- **何か** — 「桜」テーマの飾りの花を、画像ではなく**線と曲線の組み合わせ (パス)** で描く。画像と違って、どの大きさ・どの画面の細かさでもぼやけず、色もテーマの色で塗れる
- **どう作ったか** — 花びら 1 枚を、中心の近くの丸い先 → いちばん太い所 → 先の 2 つのとがり → 切れ込み、と**3 次ベジェ曲線** (始点・終点と 2 つの「引っ張る点」で決まる曲線) と直線でなぞる。もらった絵から寸法を測った。それを 72 度ずつ回して 5 枚にし、全体を 10 度回す
- **回転の式** — 画面は下向きが y の正なので、見た目で反時計回りに θ 回すのは x' = x cosθ + y sinθ、y' = y cosθ − x sinθ
- **分けたこと** — 形を作る計算 (`ornament::Sakura`) は描画を知らない純粋なコードでテストがある。描くのは `Painter::FillPath` (Direct2D の `ID2D1PathGeometry` に `AddBezier` / `AddLine` で写して塗る)
- **よけるところ** — (前の版) シーンビューとゲームビューの四角を形から切り取っていた (Direct2D の `CombineWithGeometry` の「引き算」)。飾りをいつも背景に描くようになって要らなくなり、外した (下の「テーマパック」)
- **どこ** — `src/ui/Path.h` (形のデータ)、`src/ui/Painter.cpp` (`FillPath`)、`plugins/rm_engine/theme_seasons/editor/Ornament.*` (桜の形)

### 背景に合わせて白か黒を選ぶ (輝度とコントラスト比) と、絵を 1 色で塗る (Direct2D の効果)
- **何か** — Hub のロゴは白 1 色の絵。明るいテーマでは見えなくなるので、左の欄の色が暗ければ白、明るければ黒で描く
- **白か黒かの決め方** — 色の「見た目の明るさ」(相対輝度: 赤・緑・青を、人の目の感じ方の重み 0.2126 / 0.7152 / 0.0722 で足す。色の値はその前にガンマを外す) を出し、白との**コントラスト比**と黒とのコントラスト比 (Web のアクセシビリティの基準 WCAG と同じ式) の大きい方を選ぶ。テーマを足しても自動で合う (`theme::InkOn`。テストあり)
- **1 色で塗る** — Direct2D の**効果** (エフェクト) の 1 つ、カラーマトリックス (`CLSID_D2D1ColorMatrix`)。色を「r, g, b, a に行列を掛ける」計算で変える。色の部分を決まった色にして、透明さ (アルファ) だけを残すと、絵の形をした 1 色の絵になる。縮めるときはきれいな補間 (`HIGH_QUALITY_CUBIC`) で描く。効果の識別子のために `dxguid.lib` をリンクした
- **どこ** — `src/editor/widgets/Theme.h` (`Luminance` / `InkOn`)、`src/ui/Painter.cpp` (`ImageTinted`)、`src/editor/hub/HubScreen.cpp` (`DrawSidebar`)

### 季節の絵 (図形を重ねて 1 つの影にする・決まった乱数)
- **何か** — 季節のテーマの絵 (桜の木・太陽・浜辺・砂の城・椛・雪の結晶・降る雪・つらら・積もった雪など) を、画像ではなく線と曲線のパスで描く
- **図形を重ねて 1 つの影に** — 桜の木の花は何十個もの円を重ねて作る。パスの塗り方には「交互 (alternate)」と「巻き数 (winding)」があり、交互だと 2 つ重なった所が抜けて穴になる。巻き数で塗り、図形を全部同じ向き (時計回り) に作ると、重なった所も塗られて 1 つの影になる。向きは「符号付き面積」(頂点を順に掛け合わせた和) の正負で分かるので、逆向きの多角形は裏返してから足す
- **円と楕円** — 3 次ベジェ曲線 4 本で円になる (制御点を半径の 0.5523 倍の所に置く)
- **決まった乱数** — 花びらや葉を「ばらばらに」置くのに、種 (シード) の決まった小さな乱数 (xorshift32) を使う。毎フレーム同じ数が出るので、描き直しても絵が動かない
- **どこ** — `plugins/rm_engine/theme_seasons/editor/Ornament.*` (形。テストあり)、`Seasons.cpp` (季節ごとの絵・積もる雪)、`src/ui/Painter.cpp` (`FillPath` の winding)

### 数をドラッグで変える (無限に動かせるスライダー)
- **何か** — 数の欄の名前を左右にドラッグすると数が変わる (Unity・Blender と同じ)
- **どうやって** — ドラッグ中はカーソルを隠して最初の位置に戻し続け、マウスが「動いた量」だけを足していく (シーンビューのカメラと同じ仕組み。画面の端で止まらない)。足した量 × 速さ + 始めの値 = 今の値。速さは始めた時の値で決める (大きい数ほど速い: max(1, √|値|) × 0.03)。Shift で速く、Alt で遅く
- **どこ** — `src/editor/inspector/Inspector.cpp` (`Scrub`)

### Undo のまとめ (打つたびに反映しても、Undo は 1 回分)
- **何か** — インスペクターの欄は打つたびに値が変わる。そのままだと「1」「12」「123」がそれぞれ Undo 1 回分になるので、1 つの欄に入っている間の編集は 1 つにまとめる
- **どうやって** — 欄に入るたびに番号 (まとめの鍵) を作り、編集にその番号を付ける。履歴に積むとき、一番新しい記録が同じ番号・同じ欄なら、新しい記録は作らずに「どこまで変わったか」だけを書き換える (Qt の `mergeWith` と同じ考え)。何かを Undo した後はまとめない (やり直しの記録が消えるので)。打ってから Esc で元に戻し、結局何も変わらなかったら記録ごと消す
- **ワールドの値を打つ** — 見せているのは親を含めた値なので、打った値を「親から見た値」に直してから記録する。位置は親のワールド行列の逆行列を掛ける。回転は親の回転を打ち消す。大きさは親がその軸をどれだけ伸ばしているかで割る。打った所だけを変える (位置を打って回転が少しずれる、ということがない)
- **どこ** — `src/core/UndoHistory.*` (`MergeWith`)、`src/core/reflect/FieldCommand.*`、`src/editor/inspector/Inspector.cpp`、`plugins/rm_engine/space3d/runtime/Transform.cpp` (`FromWorld`)

### ギズモ (3D の物をマウスでつかんで動かす・回す・大きさを変える)
- **何か** — 3D ツールでおなじみの、選んだ物に出る矢印・輪・箱。つかんでドラッグすると物が動く。Unity と同じ操作 (W / E / R・X でローカル / ワールド・Ctrl で刻む)
- **マウスの点 → 3D の線 (レイ)** — 画面の点を、カメラの行列の逆行列で「手前の面」と「奥の面」の 2 点に戻すと、その 2 点を通る線がマウスの指している 3D の線になる
- **矢印で動かす** — 「マウスの線」と「矢印の軸の線」の、一番近づく所を出す (2 本の線の最近点。内積の式 1 つ)。つかんだときからそこがどれだけ進んだかが動いた量
- **面の四角で動かす** — 「マウスの線」と「面」の交わる点 (レイと平面の交点)
- **輪で回す** — 輪をつかんだ点で、輪が前に進む向き (軸 × 中心からの向き の外積) を画面に写す。マウスがその向きに動いた長さ ÷ 輪の半径 (ピクセル) = 回った角度 (ラジアン)。輪を真横から見ていても回せる
- **回転を数字に戻す** — 回した結果は行列 (軸のまわりの回転 = ロドリゲスの式) で計算し、インスペクターに出すオイラー角 (X → Y → Z の角度) に戻す。同じ向きを表す角度の組は 2 つ (と 360 度ずつずらしたもの) あるので、**いま出ている数字に一番近い組**を選ぶ (179 度 → 181 度が -179 度に飛ばない)。真上・真下を向いたとき (ジンバルロック) は Z を変えずに X だけで表す
- **親がいるとき** — 動いた量・回す軸はワールドで計算し、親のワールド行列の逆行列で「親の中の量」に直してから Transform に足す (Transform は親から見た値なので)
- **いつも同じ大きさに見せる** — カメラからの奥行きに比例して大きくする (1 ピクセルが何 m か = 2 × 奥行き × tan(視野角 / 2) ÷ 画面の高さ)
- **Undo** — ドラッグ中は値を直接変え、離したときに「前の値 → 後の値」を 1 つの Undo (いくつも選んでいればまとめて 1 つ) にして積む
- **どこ** — `plugins/rm_engine/space3d/editor/Gizmo.*` (計算。テストあり)、`plugins/rm_engine/space3d/runtime/Transform.cpp` (回転の行列と角度)、`plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp` (描く・ドラッグ)

### ドッキング (木で配置を持つ)
- **何か** — パネルをタブにしたり、分割したり、別のウィンドウに出したりする仕組み
- **どう作ったか** — 配置を「木」で持つ。節は「分割 (向きと比率)」か「葉 (タブの並び)」。パネルを動かす = 木から抜く → 入れる → 空いた所をたたむ。この木の操作は描画から切り離した純粋なコードで、テストがある
- **ウィンドウをまたぐ** — ドラッグ中、マウスの下にあるウィンドウを Windows に聞いて (`WindowFromPoint` に相当する処理)、そのウィンドウに目印を出す
- **保存** — 配置はプロジェクトの `UserSettings/Layout.json` に JSON で
- **名前を付けた配置** — 今の木を JSON にして名前と一緒に一覧に入れておき、選んだら JSON から木を作り直す (消えたパネルは `Sanitize` で外す)。名前などの項目はリフレクション (`RM_STRUCT`) で保存し、知らないキーは書き戻す
- **入りきらないタブの列** — タブの幅を全部足した長さと、見える幅から「どれだけずらすか」(スクロール量) を計算する。表に出したタブが見えるように動かす量・‹ › で次のタブの端まで動かす量・落とした所が何番目かも、画面から切り離した計算 (テストあり)。見える所の外は「切り抜き (クリップ)」で描かず、押せない
- **どこ** — `src/editor/dock/DockLayout.*` (木とタブの列の計算)、`NamedLayouts.*` (名前を付けた配置)、`DockSpace.*` (描画と入力)

### 木の表示 (階層)
- **何か** — 開く・閉じる・選ぶ (Ctrl / Shift)・ドラッグで並べ替え・名前の変更・検索 ができる木の表示
- **どう作ったか** — 核は木の見せ方だけを持ち、何を並べるかはソフトが決める (インターフェース `tree::Source`)。「見える行」「選択」「どこに落とすか」は純粋な計算でテストがある
- **どこ** — `src/editor/tree/*`

### 色のテーマ (黒・白・PC に合わせる)
- **何か** — 画面の色を 2 つの組 (黒と白) で持ち、切り替える仕組み
- **どう作ったか** — 色は全部 `theme::` の変数を通して使うので、変数の中身を入れ替えるだけで全部の画面が変わる。タイトルバーは DWM の `DWMWA_USE_IMMERSIVE_DARK_MODE` / `DWMWA_CAPTION_COLOR` で合わせる
- **PC に合わせる** — Windows の設定はレジストリ `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` の `AppsUseLightTheme` にある。Windows は設定が変わると全部のウィンドウに `WM_SETTINGCHANGE` ("ImmersiveColorSet") を送るので、それを受けて読み直す
- **どこ** — `src/editor/widgets/Theme.h`、`src/platform/Window.cpp` (`SetCaption`)、`src/platform/Shell.cpp` (`SystemPrefersLight`)

### 多言語化 (日本語の文を鍵にした翻訳表)
- **何か** — 画面の文字を言語に合わせて出し分ける仕組み (i18n)。gettext という有名な仕組みと同じ考え方で、**元の言語 (日本語) の文そのものを鍵**にして、英語の表 (JSON) を引く
- **良い点** — コードを読めば何が出るか分かる (番号や英字の ID にしない)。英語が無い文は日本語のまま出るので、訳し忘れても画面が壊れない
- **訳し忘れを止める** — ビルドのたびに `tools/check_lang.ps1` がソースを読み、`Tr(L"…")` などの文と、リフレクションの項目名に英語があるかを調べる。`{}` (std::format の差し込み) の数が違っても失敗にする
- **std::vformat** — 訳した文に値を差し込むのは、実行中に決まる書式で `std::vformat` を使う (書式が合わなければ日本語の書式に戻る)
- **どこ** — `src/editor/lang/*`、`resources/lang/en.json`、`plugins/*/*/lang/en.json`、`tools/check_lang.ps1`

### 自動保存 (タイマー)
- **何か** — Windows のタイマー (`SetTimer` → `WM_TIMER`) で 15 秒ごとに起き、未保存の変更が決めた時間たっていれば保存する
- **工夫** — 入力中・ドラッグ中 (`GetKeyState` でマウスのボタン)・ダイアログ中は保存しない。何も起きていないときは描かない作り (CPU 0%) を崩さないよう、タイマーは描画せずに見るだけ
- **どこ** — `src/editor/shell/EditorScreen.cpp` (`OnTimer`)

## 5. データと保存

### 自作の JSON
- **何か** — 人が読める文字のデータ形式。RM Engine の保存ファイル (`.rmpf`・`Layout.json`・`hub.json`・`plugin.json`) は全部 JSON
- **なぜ自作か** — **キーの順番を保ったまま読み書きし、知らないキーも捨てずに書き戻す**ため。新しい版で保存したファイルを古い版で開いて保存しても、データが消えない。読み書きを繰り返してもバイト単位で同じになる (テストあり)
- **どこ** — `src/base/Json.*`

### リフレクションとコード生成 (rmgen)
- **何か** — リフレクション = プログラムが自分のデータの形 (フィールドの名前・型) を知っている仕組み。C++ には無いので、ヘッダーを読んで表を作る小さなツール (rmgen) を自作した
- **何に使っているか** — データの型を 1 か所に書くだけで、保存・読み込み・インスペクター (編集画面)・比較・Undo・値の範囲の制限 がそこから出る
  ```cpp
  RM_STRUCT(Label="ゲームの設定")
  struct GameSettings {
      RM_PROPERTY(Edit, Label="目標 FPS", Min=1, Max=240) int targetFps = 60;
  };
  ```
- **仕組み** — `RM_PROPERTY` などは中身が空のマクロ (目印)。ビルドの最初に rmgen がヘッダーを読み、型の表 (`TypeDesc`) を C++ のコードとして書き出す。保存やインスペクターは、どの型でもこの表を辿る共通の関数 1 本ずつ
- **書き忘れを止める** — 目印の無いフィールドは rmgen がエラー (`error RM0001` とヘッダーの行・列) にする。ヘッダーを変えて rmgen を通さないと、生成したコードの `static_assert` (コンパイル時の検査) が「フィールドの数」(集成体のメンバーの数を C++20 の `requires` で数える) と名前・型の食い違いで止める
- **なぜそれか** — 前のエンジンでは保存・読み込み・編集画面を型ごとに手で書き、書き忘れやずれで不具合が出た。1 か所に書けばずれようがない
- **どこ** — `src/core/reflect/*`、`tools/rmgen/*`、`src/RM.Reflect.targets` (MSBuild に組み込む)

### Undo (コマンドパターン)
- **何か** — 「やったこと」を `Do` / `Undo` を持つ小さなオブジェクト (コマンド) にして積んでおく作り方
- **何に使っているか** — 編集の取り消しとやり直し。**Undo に積んだ = 未保存** と決めているので、編集が保存されずに消えることがない
- **工夫** — どの型のどのフィールドの変更も 1 種類のコマンド (`SetFieldCommand`、リフレクションで値を出し入れ) で表す。シーンの形の変更 (作る・消す・動かす) は前後の状態を持つコマンド。Undo の途中で新しいコマンドを積もうとしたら断る (前のエンジンの不具合の再発防止)
- **どこ** — `src/core/UndoHistory.*`、`src/core/reflect/FieldCommand.*`

### 型を消した値 (type erasure)
- **何か** — 「何の型か」をコンパイル時に決めず、実行中に型の表 (`TypeDesc`) を見て値を作る・写す・壊す入れ物
- **何に使っているか** — エンティティの部品 (コンポーネント)。ゲーム制作は Transform という型を知らないが、型の表があれば Transform の値を持てる
- **どう作ったか** — 型の表の大きさでメモリを取り、表の construct (既定値で作る)・copy・destruct を呼ぶ。C++ の「5 つの特別な関数」(コピー・移動・代入・デストラクタ) をきちんと書いて、ふつうの値と同じに使える
- **どこ** — `src/core/reflect/Object.*`

### 整合性の確認 (SHA-256)
- **何か** — ファイルの中身から 32 バイトの「指紋」(ハッシュ) を作る計算 SHA-256 で、ファイルが壊れていないか・入れ替わっていないかを確かめる。Steam の「ゲームファイルの整合性を確認」と同じ考え方
- **どう作ったか** — ビルドの最後に PowerShell の `Get-FileHash` でエンジンのファイルの一覧と指紋を JSON に書く。確認のときは Windows の暗号の仕組み BCrypt (`BCryptHashData`) で指紋を計り直して比べる
- **限界** — 一覧そのものに署名が無いので、悪意のある書き換えは防げない (壊れた・欠けた・古いを見つけるためのもの)
- **どこ** — `tools/make_filelist.ps1`、`src/editor/app/Integrity.*`、`src/platform/Shell.cpp` (`Sha256File`)

### 埋め込みリソース
- **何か** — 画像や JSON を exe の中に入れておく Windows の仕組み (`.rc` ファイルの `RCDATA`)。ファイルを無くす心配が無い
- **何に使っているか** — Hub のロゴ、アップデート情報 (`resources/updates.json`)
- **どこ** — `resources/app.rc`、`platform::ResourceBytes`

### 知らないデータを捨てない
- 新しい版のファイルや、プラグインが無い状態で開いたファイルでも、分からないキー・分からない選択肢の名前を覚えておいて、保存のときにそのまま書き戻す (`reflect::Unknowns`)
- 選択肢 (列挙) は番号ではなく**名前**で保存する。選択肢の順番を変えても古いファイルの意味が変わらない

## 6. プラグイン

### 静的リンクのプラグイン
- **何か** — 機能 (ソフト) をプラグインとして分けて作る仕組み。コードは exe に全部入れておき (静的リンク)、「インストールしたものだけ有効にする」
- **なぜそれか** — DLL を後から読み込む方式より簡単で安全 (読み込み失敗やバージョン違いが起きない)。プラグインを足すときは `plugins/<作者>/<名前>/` にフォルダを足すだけ (プロジェクトファイルはワイルドカードで全部拾う)
- **plugin.json** — プラグインの ID・名前・前提 (requires) を書く。コードの中の ID と照らし合わせ、食い違えば使わない
- **前提の解決** — 前提のプラグインを先に並べる (トポロジカルソート)、輪になっていないか・欠けていないかを調べる。純粋な計算でテストあり
- **柵** — 核 (`src/`) はプラグインを知らない。プラグインは `requires` に書いたものしか `#include` できない。ゲームに入る部分 (`runtime/`) はエディターの部分 (`editor/`) を使えない。全部 `check_layers.ps1` が調べる
- **どこ** — `src/editor/plugin/*`、`plugins/*`

### つなぎプラグイン (前提の向きを 1 方向にする)
- **何か** — 2 つのプラグインの「両方を知らないと作れない部分」だけを、両方を前提にした 3 つ目のプラグインに切り出す作り方
- **何に使っているか** — ゲーム制作は 3D も 2D も知らずに作り、「ゲーム制作 × 3D」が 3D 空間の Transform をゲームの部品として渡す。2D のゲームに 3D の部品が入らない
- **なぜそれか** — ゲーム制作が 3D 空間を直接読むと、使わないゲームにも 3D が入る。つなぎの方からだけ矢印を向けると、前提が輪にならない
- **決まり** — `plugin.json` に `needsConnector` (つなぎが要る) と `connectorFor` (誰のつなぎか)。つなぎが 1 つも使えないと、つなぎが要る側は使えない。つなぎは要るものがそろうと自動で入る
- **どこ** — `src/editor/plugin/PluginManifest.cpp`、`plugins/rm_engine/game_x_3d/`

### テーマパック (ファイルだけのプラグイン) と、背景に描く飾り
- **何か** — 色のテーマを、JSON のファイル (`themes/*.json`) を持つプラグインとして足す作り。コードの無いプラグインもふつうに「インストール」「削除」できる。絵 (季節の飾り) が要るパックは、その絵を描く関数を差し出しの口に渡す
- **背景に描く工夫** — 飾りをウィンドウの最後に重ねると文字にかぶる。そこで、ウィンドウの地・パネルの地・帯の地を塗るたびに、**ウィンドウ全体の同じ絵をその四角で切り取って (クリップして) 描き直す**。どこでも絵は地のすぐ上・中身のすぐ下になる。何度も描くので、ウィンドウの大きさごとに作った形を覚えておく (キャッシュ)
- **どこ** — `src/editor/widgets/ThemeFile.*` (読み込み)、`Widgets.cpp` (`DrawBackdrop` / `DrawBackdropOn`)、`src/editor/app/App.cpp` (`LoadThemes`)、`plugins/rm_engine/theme_*`

### 差し出しの口 (拡張ポイント)
- **何か** — プラグインが別のプラグインへ物を渡すための、名前の付いた口。渡す側と受け取る側は直接お互いのコードを呼ばず、核の登録簿 (`PluginRegistry`) を通す
- **何に使っているか** — 「ゲーム制作 × 3D」が Transform を `rm_engine.game_production.component` の口に差し出し、ゲーム制作がそこから部品の種類を集める
- **工夫** — 物は `const void*` で預かるが、預けた型 (`typeid`) も覚えておき、違う型として取り出そうとしたら渡さない (型の安全)
- **どこ** — `src/editor/plugin/Software.h` (`Contribute` / `Contributions`)

## 7. テストと品質

- **自作の小さなテストの仕組み** — `RM_TEST(名前) { CHECK(条件); }` で書く。失敗があれば終了コードが 0 以外になり、CI が気づく (`tests/Test.h`)
- **純粋な計算を分けてテストする** — 画面やファイルを使わない部分 (JSON・Undo・ドッキングの木・プラグインの前提・リフレクション・階層・シーン) はテストがある。テストは GPU もファイルも使わない
- **わざと壊して確かめる** — 層の検査は、違反をわざと入れて全部見つかることを確かめた
- **ログ** — `%LOCALAPPDATA%\RM_Engine\Logs\editor.log` に書き、同じものをエディターのコンソールに出す (複数のスレッドから書いても壊れないように `std::mutex`)

## 8. ゲーム制作と 3D 空間のいま

- **シーンとエンティティ** — エンティティは `id`・親の `id`・名前・有効 を持つ (リフレクションで定義)。並びの順 = 兄弟の順。ID は使い回さない。壊れたファイル (同じ ID・無い親・親の輪) は読み込むときに直す
- **どこ** — `plugins/rm_engine/game_production/runtime/Scene.*`

### ECS (エンティティ・コンポーネント・システム) の「C」
- **何か** — ゲームの物 (エンティティ) を、部品 (コンポーネント: 位置・見た目・当たり判定 …) の組み合わせで作る考え方。物の種類ごとにクラスを作る (継承) のではなく、部品を付け外しして作る。S (システム) は部品を持つ物を毎フレーム動かす処理 (まだ作っていない)
- **何に使っているか** — エンティティは部品を型ごとに 1 つまで持つ。インスペクターで足す・外す・値を変える。全部 Undo できる
- **保存** — 部品は型の名前 (C++ の名前) と値で保存。プラグインが無くて使えない部品も、読んだまま書き戻して消さない
- **どこ** — `plugins/rm_engine/game_production/runtime/Components.h`、`Scene.*`

### 3D の座標変換 (行列とオイラー角)
- **何か** — 物の位置・回転・大きさを 4×4 の行列 1 つにまとめ、点に掛けると「その物の中の点が世界のどこにあるか」が出る計算。親子のときは親の行列 × 子の行列
- **決まり** — 列ベクトル (`p' = M × p`)。大きさ → 回転 → 移動 の順。回転は度で持ち、X 軸 → Y 軸 → Z 軸 の順に回す (オイラー角)
- **どこ** — `plugins/rm_engine/space3d/runtime/Transform.*` (テスト: `tests/TestSpace3d.cpp`)

---

### Direct3D 11 での 3D 描画 (シェーダー)
- **何か** — GPU に 3D の形を描かせる仕組み。頂点 (点) を並べたバッファ・それを画面に置く**頂点シェーダー**・色を決める**ピクセルシェーダー**・手前の物だけを残す**深度バッファ**で描く
- **何に使っているか** — 3D 空間プラグインの描画の部分が、シーンビューの床のグリッド・軸・箱を描く
- **シェーダー** — HLSL という GPU 用の言語でコードの中に書き、最初に使うときに `D3DCompile` (Windows に入っている) で GPU 用に変換する。箱は「光の向きと面の向きの角度」で明るさを変える (ランバート反射) + 空からの明かりを少し
- **定数バッファ** — 行列や色を GPU に渡す箱。行列は「列ごと」に並べて持っていて、HLSL の決まりと同じなので、そのまま渡せる
- **MSAA (マルチサンプル アンチエイリアス)** — 1 ピクセルを 4 つに分けて描き、最後に混ぜる (`ResolveSubresource`)。線のギザギザが消える
- **どこ** — `plugins/rm_engine/space3d/runtime/Renderer3D.*`

### Direct3D と Direct2D を混ぜる
- **何か** — 3D は Direct3D、UI は Direct2D で描いているが、同じ GPU (デバイス) を使っているので、Direct3D で描いたテクスチャを Direct2D の画像 (ビットマップ) としてそのまま貼れる (`CreateBitmapFromDxgiSurface`。コピーしない)
- **工夫** — Direct2D の描きかけを先に GPU へ送り (`Flush`)、3D は別のテクスチャに描く。絵の大きさは画面のピクセル数に合わせる (高 DPI でもぼやけない)
- **どこ** — `plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp`

### 3D のカメラとクリックで選ぶ (レイ)
- **透視投影・LookAt** — 遠くの物ほど小さく見せる行列と、カメラの位置と向きから作る行列。右手系・Y が上
- **逆行列** — 行列を元に戻す行列。「画面のこの点」から「3D 空間のどの向き」かを逆にたどるのに使う
- **レイとの当たり** — クリックした点から 3D 空間へ光線 (レイ) を飛ばし、どの箱に最初に当たるかを調べる。箱は「スラブ法」(x・y・z の 3 方向の板に挟まれた区間が重なるか) で調べる。回したり大きくしたりした箱は、レイの方を箱の向きに戻してから調べる
- **編集用のカメラ** — 見ている点 (ピボット)・左右の角度・上下の角度・距離で持つ。見回す (目が動かない) / 回る (見ている点が動かない) / 平行移動 / 近づく / 飛ぶ を計算で分けている
- **どこ** — `plugins/rm_engine/space3d/runtime/View.*` (テスト: `tests/TestSpace3d.cpp`)

### 3D モデルのファイルを読む (glTF 2.0 / GLB / OBJ)
- **何か** — Blender などで作った 3D モデルの形 (頂点の位置・法線・UV と、それをつなぐ三角形) をファイルから読む
- **glTF 2.0** — Khronos が決めた「3D の JPEG」と呼ばれる形式。中身は JSON (どのバイト列が何か: `buffers` → `bufferViews` (バイト列の区切り) → `accessors` (「ここから float が 3 つずつ 100 組」) → `meshes` の `primitives` (位置・法線・UV・インデックス)) と、バイナリー (数の並び)。`.gltf` は JSON とバイナリーが別ファイル (か、バイナリーを base64 で JSON の中に埋め込む `data:` URI)、`.glb` は 1 つのファイル (12 バイトの見出し + JSON のかたまり + バイナリーのかたまり)
- **ノード** — glTF は物の置き場所を木で持つ (ノード = 行列か 位置・回転 (四元数)・大きさ)。親から子へ行列を掛けていき、頂点に焼き込んで 1 つの形にする。鏡に映す行列 (大きさがマイナス) のときは三角形の向きが裏返るので、頂点の順を入れ替えて表を保つ
- **OBJ** — 古くからある文字の形式。`v` (位置)・`vt` (UV)・`vn` (法線)・`f` (面: 頂点の番号。1 から数える、マイナスは後ろから)。多角形は扇形に三角形に切る。同じ番号の組 (v/vt/vn) は 1 つの頂点にまとめる (ハッシュ表)
- **法線を作る** — ファイルに法線が無ければ、三角形の 2 辺の外積 (長さ = 面積の 2 倍) を頂点ごとに足して長さ 1 にする (大きい面ほど強く効く、なめらかな法線)
- **外部ライブラリを使わない理由** — 要るのは形だけで、glTF は今ある自作の JSON で読める (cgltf や tinygltf を入れるほどではない)。壊れたファイルでも落ちないよう、数を読む前に「バッファーからはみ出さないか」を全部確かめる
- **どこ** — `plugins/rm_engine/space3d/runtime/Mesh.*` (純粋。テスト: `tests/TestSpace3d.cpp`)、`MeshFile.*` (ファイルを読むだけ)。サンプル: `docs/samples/models/`

### GPU にモデルを 1 回だけ上げる
- **何か** — 頂点とインデックスを GPU のメモリー (`ID3D11Buffer`。`IMMUTABLE` = 書いたら変えない) に 1 回だけ写して、毎フレームはそれを指して描くだけにする。同じモデルを使う物が何個あっても 1 つ
- **工夫** — シーンビューがファイルのパスごとに覚え、1 秒ごとにファイルの更新時刻を見て、変わっていたら読み直す (3D ツールから書き出し直すとすぐ映る)。しばらく使われないものは捨てる (`shared_ptr` で、最後に使う物がいなくなると GPU のメモリーも返る)
- **どこ** — `Renderer::Upload` (`plugins/rm_engine/space3d/runtime/Renderer3D.*`)、`plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp`

### 影 (シャドウマップと PCF)
- **シャドウマップ** — まず光の位置から見た「一番手前の物までの深さ」だけの絵 (深度テクスチャ) を描く。次に普通に描くとき、各ピクセルが「光から見た自分の深さ」とその絵の深さを比べ、絵の方が手前なら間に何かある = 影
- **平行光と正射影** — 太陽のような平行な光なので、光から見る行列は遠近の無い正射影。影を落とす物全部を囲む箱が、ちょうどその正射影に収まるように作る (物が動かない限り変わらないので、カメラを動かしても影がちらつかない)
- **PCF (Percentage Closer Filtering)** — 1 か所だけで比べると影の縁がギザギザになるので、周りの 3 × 3 か所で比べて「何割が影か」を明るさにする。GPU の**比較サンプラー** (`SamplerComparisonState` + `SampleCmpLevelZero`) は 1 回で 2 × 2 の比べた結果を混ぜてくれるので、さらになめらか
- **影のにきび (shadow acne) を防ぐ** — 面が自分自身の影になって縞模様が出るのを、深さを少しずらす (傾きに比例したずれ `SlopeScaledDepthBias` + テクセル 1 つ分) のと、法線の向きに少しずらした所で比べる (normal offset) ので防ぐ
- **1 枚のテクスチャを 2 通りに見る** — `R32_TYPELESS` で作り、書くときは深度 (`D32_FLOAT` の DSV)、読むときは数 (`R32_FLOAT` の SRV) として使う
- **床の影** — Y = 0 に見えない大きな板を置き、影の所だけ半透明の色を重ねる (深度は書かないので、グリッドの線はその上に乗る)
- **どこ** — `plugins/rm_engine/space3d/runtime/Renderer3D.*` (HLSL も中)、光の行列は `View.*` の `DirectionalShadowMatrix` (純粋。テストあり)

### ドラッグを画面の端で止めない (マウスの固定)
- **何か** — カメラを回すドラッグの間、カーソルを隠して、動くたびに**ドラッグを始めた点へ戻す** (`SetCursorPos`)。戻す前に「どれだけ動いたか」を数えるので、マウスを動かした分だけいくらでも回せる。ゲームの「マウスでの視点操作」や Unity / Blender の見回しと同じやり方
- **工夫** — 戻したときに Windows が出す「マウスが動いた」の知らせは、ちょうど始めた点なので「動いた量 0」になり、二重に数えない。ボタンを離すとカーソルが元の場所に出てくる
- **どこ** — `src/editor/app/ScreenWindow.cpp` (`MouseMoved` / `UpdateMouseLock`)、`src/ui/Context.h` (`LockMouse`)

### 押し続けるキーと、描き続けるフレーム
- このエンジンは何も起きていないときは描かない (CPU を使わない)。カメラで飛ぶときは「キーを押している間ずっと動く」必要があるので、**キーが押されているか** (`WM_KEYDOWN` / `WM_KEYUP` で覚える) と、**頼まれている間は次のフレームをすぐ描く** (`RequestAnimation`) を足した。キーを離せばまた止まる
- **どこ** — `src/ui/Context.h`、`src/editor/app/ScreenWindow.cpp`

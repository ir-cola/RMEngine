# 使っている技術のメモ

RM Engine で使っている技術と、これから使う予定の技術をまとめる。人に説明できるようにするためのメモ。
**機能を足して新しい技術を使ったら、ここに書き足す** (一番下の「追記の記録」にも 1 行足す)。

1 つの技術は次の形で書く。

- **何か** — その技術の一言の説明
- **何に使っているか** — RM Engine の中での役目
- **なぜそれか** — 選んだ理由 (ほかの選択肢と比べて)
- **どこ** — コードの場所

---

## 1. 全体の形

RM Engine は「ゲーム・イラスト・作曲・3D モデルなどを、プラグインを足して 1 つのソフトで作る」ための制作環境。
Windows のデスクトップアプリで、C++ で一から書いている (既製のゲームエンジンや UI ライブラリは使っていない)。

```
src/base      L0  文字列・JSON・ログ (Windows も知らない純粋な部品)
src/core      L2  Undo・リフレクション・プラグインの ID
src/platform  L3  Windows: ウィンドウ・GPU・ファイル・ダイアログ
src/ui        L4  UI の土台 (入力・文字の編集・描画の受け口)。色は持たない
src/editor    L6  Hub・エディターの枠・パネル・インスペクター・階層 (ゲームには入らない)
plugins/            ソフトはプラグインで足す (いまは「ゲーム制作」)
```

- 番号の小さい層は大きい層を知らない (下から上へだけ依存する)。こうすると、ゲームに入れる部分 (L0〜L4) からエディターを切り離せる
- この決まりは `layers.txt` に書き、`tools/check_layers.ps1` がビルドのたびに `#include` を全部調べて破っていないか確かめる (4-3)

## 2. 言語と開発環境

### C++20
- **何か** — C++ の 2020 年版の規格
- **何に使っているか** — エンジン全部
- **なぜそれか** — 描画やファイルを細かく速く扱える。C++20 の `std::format` (文字の組み立て)・`std::span` (配列の一部を渡す)・`consteval` (コンパイル時の検査)・`requires` (型の条件)・`<=>` / `= default` の比較 を使っている
- **どこ** — 全部。例: プラグイン ID をコンパイル時に検査する `consteval PluginIdLiteral` (`src/core/PluginId.h`)

### Visual Studio 2022 / MSBuild
- **何か** — Microsoft の開発環境と、そのビルドの仕組み
- **何に使っているか** — ビルド (`RM_Engine.sln` と各 `.vcxproj`)。共通の設定は `src/RM.Common.props` に 1 か所
- **なぜそれか** — 対象が Windows だけなので、Windows の機能とデバッガーを一番うまく使える (ユーザーの決定)
- **設定** — `/W4` (警告を多めに出す) で警告 0 を保つ / `/utf-8` (ソースは UTF-8) / 静的 CRT (配るときに追加のランタイムが要らない) / x64

### Git と GitHub Actions (CI)
- **何か** — 変更の記録 (Git) と、プッシュのたびに自動でビルドする仕組み (CI)
- **何に使っているか** — https://github.com/ir-cola/RMEngine (非公開)。プッシュすると Windows のマシンで Debug と Release をビルドし、テストと層の検査まで通るか確かめる
- **どこ** — `.github/workflows/ci.yml`、`tools/build.ps1`

### PowerShell
- **何に使っているか** — ビルドの手順 (`tools/build.ps1`: ビルド → テスト → 層の検査)、層の検査 (`tools/check_layers.ps1`)、アイコンとロゴの作成 (`tools/make_resources.ps1`: .NET の System.Drawing で PNG から .ico を作る)
- **なぜそれか** — Windows に最初から入っていて、追加のツールが要らない

## 3. Windows と描画

### Win32 API (ウィンドウとメッセージ)
- **何か** — Windows のアプリの一番下の仕組み。ウィンドウは「メッセージ」(マウスが動いた・キーが押された・描き直して など) を受け取って動く
- **何に使っているか** — Hub・エディター・外に出したパネルのウィンドウ。マウス (`WM_LBUTTONDOWN` …)・キー (`WM_KEYDOWN`)・文字 (`WM_CHAR`)・大きさ (`WM_SIZE`)・DPI の変化 (`WM_DPICHANGED`)。ドラッグ中はマウスを捕まえる (`SetCapture`)
- **なぜそれか** — 余計な層が無く、何が起きているか全部見える。Windows だけが対象なので、間に別のライブラリを挟む理由が無い
- **どこ** — `src/platform/Window.*`、`src/editor/app/ScreenWindow.*`

### Per-Monitor DPI v2 と DIP
- **何か** — 画面の細かさ (DPI) がモニターごとに違っても、正しい大きさで描くための仕組み。DIP = 「96 DPI のときの 1 ピクセル」を単位にした長さ
- **何に使っているか** — UI は全部 DIP で考え、描くときだけ実際のピクセルに直す。モニターを移ると `WM_DPICHANGED` で描き直す
- **どこ** — `resources/app.manifest` (`PerMonitorV2`)、`GetDpiForWindow`

### Direct3D 11 + DXGI
- **何か** — GPU を使う Windows の描画の仕組み (D3D11) と、画面へ出す仕組み (DXGI のスワップチェーン)
- **何に使っているか** — いまは Direct2D の土台。これからシーンビューや 3D の描画もここに乗る
- **なぜそれか** — Windows ならどの PC でも動き、情報も多い。D3D12 より書く量が少ない
- **どこ** — `src/platform/Gfx.*`

### GPU が失われたとき (デバイスの消失と作り直し)
- **何か** — ドライバーの更新・ドライバーの落ち直し・GPU が固まったときに Windows が GPU をリセットする仕組み (**TDR**: Timeout Detection and Recovery) などで、アプリの Direct3D のデバイスは「失われる」(`DXGI_ERROR_DEVICE_REMOVED`)。そのデバイスで作った物 (スワップチェーン・テクスチャ・バッファ・シェーダー・Direct2D のビットマップやブラシ) は全部使えなくなる。直す方法は**デバイスから全部作り直す**ことだけ
- **知る方法** — `ID3D11Device::GetDeviceRemovedReason()` が S_OK 以外 / Direct2D の `EndDraw` が `D2DERR_RECREATE_TARGET` / `Present` が `DXGI_ERROR_DEVICE_REMOVED` か `DXGI_ERROR_DEVICE_RESET`
- **このエンジンのやり方** — デバイスを作った回数 (世代の番号) を 1 つ持ち、GPU の物を持つ所はそれぞれ「作ったときの番号」を覚える。番号が変わったら自分の物を捨てて、要るときに作り直す (全部を知る 1 か所の一覧を作らないので、プラグインが増えても同じ形で乗れる)
- **ファクトリーは残る** — Direct2D / DirectWrite / WIC のファクトリーは CPU の側の物なので、作り直さなくてよい (図形と文字の書式もそのまま)
- **試し方** — Windows の「グラフィックス ツール」の `dxcap -forcetdr` で本当に TDR を起こせる。このエンジンには、失われたことにして同じ道を通る口 (Ctrl+Alt+Shift+F12) もある
- **どこ** — `src/platform/Gfx.*` (`Generation` / `Lost` / `Recreate` / `MarkLost`)、`src/editor/app/ScreenWindow.cpp` (`EnsureDevice`)、`src/editor/app/App.cpp` (`RecoverGraphics`)

### Direct2D / DirectWrite
- **何か** — GPU で 2D の図形 (Direct2D) と文字 (DirectWrite) を描く Windows の仕組み
- **何に使っているか** — エディターの UI 全部 (四角・角丸・線・文字・画像)。日本語の文字、文字の幅の計測、はみ出したときの「…」、折り返しも DirectWrite
- **なぜそれか** — きれいな文字 (ClearType・日本語) をすぐに出せる。D3D11 と同じ GPU の上で動く
- **どこ** — `src/ui/Painter.*` (描く命令の受け口)、`src/platform/Gfx.*`

### WIC (Windows Imaging Component)
- **何か** — Windows に入っている画像の読み込みの仕組み (PNG・JPEG・BMP・GIF・TIFF …)。ファイルの頭のバイトを見て形式を当て、合うデコーダー (解く部品) を選んでくれる
- **何に使っているか** — Hub のロゴ (exe に埋め込んだ PNG)・3D モデルのテクスチャ・アセットのパネルのサムネイル。全部 `platform::DecodeImage` の 1 本を通る
- **流れ** — バイト列 → `IWICStream` (メモリーの上のファイルのふり) → `CreateDecoderFromStream` → 1 枚目の絵 (`GetFrame(0)`) → 大きすぎれば `IWICBitmapScaler` で縮める (Fant = 縮めるのにきれいな方法) → `IWICFormatConverter` で欲しい並び (テクスチャは RGBA、Direct2D は事前乗算の BGRA) → `CopyPixels` で自分の配列へ
- **事前乗算 (premultiplied) アルファ** — 色にあらかじめ透明度を掛けておく持ち方 (半分透けた赤 = (0.5, 0, 0, 0.5))。重ねる計算が 1 回の掛け算と足し算で済み、縁がにじまない。Direct2D はこの形が基本
- **なぜそれか** — Windows に最初から入っていて、配るものが増えない (libpng や stb_image を入れなくてよい)。TGA は読めないので、要るときに小さく自作する予定 (9 章)
- **どこ** — `src/platform/Image.*` (`DecodeImage` / `LoadImageFile` / `BitmapFromImage`)、`src/platform/Gfx.cpp` (`LoadBitmapFromMemory` もこれを通す)

### IME (IMM32)
- **何か** — 日本語入力 (かな漢字変換) を受け取る Windows の仕組み
- **何に使っているか** — 入力欄で日本語を打てるようにする。変換中の文字 (下線付き) と確定した文字を受け取り、候補の窓を入力欄のカーソルの位置に出す
- **どこ** — `src/editor/app/ScreenWindow.cpp` (`WM_IME_COMPOSITION` など)、`src/ui/TextEdit.*`

### DWM (デスクトップ ウィンドウ マネージャー)
- **何に使っているか** — タイトルバーを暗い色にする (`DWMWA_USE_IMMERSIVE_DARK_MODE` / `DWMWA_CAPTION_COLOR`)、ウィンドウの見えている本当の四角を知る (`DWMWA_EXTENDED_FRAME_BOUNDS`。ドッキングでマウスの下のウィンドウを探すとき)
- **どこ** — `src/platform/Window.cpp`、`src/platform/Shell.cpp`

### シェルと COM
- **何か** — COM は Windows の部品を呼び出す仕組み。シェルはエクスプローラーまわりの機能
- **何に使っているか** — 「開く」「フォルダを選ぶ」のダイアログ (`IFileOpenDialog`)、エクスプローラーでファイルを選んだ状態で開く (`SHOpenFolderAndSelectItems`)、ドキュメントや AppData の場所 (`SHGetKnownFolderPath`)
- **どこ** — `src/platform/Shell.*`

### フォルダの変化を知る (変更通知) とごみ箱
- **何か** — Windows に「このフォルダの下でファイルが増えた・消えた・名前が変わったら教えて」と頼む仕組み (`FindFirstChangeNotification` / `FindNextChangeNotification`) と、ファイルを消す代わりにごみ箱へ移す仕組み (`IFileOperation` と `FOFX_RECYCLEONDELETE`)
- **完全に消さないために** — ごみ箱の無い所 (USB メモリ・ネットワーク) や、ごみ箱より大きいファイルは、ごみ箱へ移すつもりでも Windows が完全に消してしまう (確認を出さない設定だと黙って)。`IFileOperation` に「進み具合の受け手」(`IFileOperationProgressSink`) を付けると、1 つ消す前ごとに `PreDeleteItem` が呼ばれ、そのとき「ごみ箱へ行けるか」の印 (`TSF_DELETE_RECYCLE_IF_POSSIBLE`) が分かる。印が無ければ取り消しの値を返して、その物は消さない
- **何に使っているか** — アセットのパネル。エクスプローラーでファイルを動かしたら、エディターに戻ったときにパネルが付いていく。パネルの「削除」はごみ箱へ (戻せる)
- **どう使っているか** — 通知はスレッドで待たず、描くたびに「来ているか」だけを 0 秒で聞く (`WaitForSingleObject(…, 0)`)。来ていたらフォルダを読み直す。自分で書いたファイルでも通知は来るが、読み直して何も変わらなければそこで止まる
- **どこ** — `platform::FolderWatch` / `MoveToRecycleBin` (`src/platform/Shell.*`)、`src/editor/assets/AssetLibrary.*`

### ファイルの安全な書き方
- **何か** — まず `<ファイル>.tmp` に書いてディスクまで書き切り (`FlushFileBuffers`)、それから置き換える (`MoveFileEx`)
- **なぜそれか** — 保存の途中で落ちても、半端なファイルが残らない (前の版か新しい版のどちらかが必ず残る)
- **どこ** — `platform::WriteFileAtomic` (`src/platform/Shell.cpp`)

### 作業スレッド (遅いディスクの処理を画面の外で)
- **何か** — 画面を描くスレッド (UI のスレッド) とは別のスレッドで、時間のかかるファイルの読み書きをする。C++20 の `std::jthread` (止めるよう頼める `stop_token` 付きのスレッド) を使い、結果は「UI のスレッドで後で動かす関数」として箱に入れ (`std::mutex` で守る)、`PostThreadMessage` でメッセージループを起こす
- **なぜそれか** — 届かないネットワークのドライブにあるプロジェクトを 1 つ読むだけで数秒かかることがあり、その間ウィンドウが固まる。画面の物 (行の一覧など) に触るのは UI のスレッドだけにしておけば、鍵 (ロック) をあちこちに付けなくてよい
- **気を付けること** — 古い結果が新しい一覧に混ざらないよう、頼み直したら前の結果は捨てる (番号で見分ける)。翻訳表やログも UI のスレッドのものなので、作業スレッドでは使わない
- **どこ** — `src/editor/app/Worker.*`、Hub (`HubScreen::Refresh`・整合性の確認)、`App::StartEngineRefresh`

### Windows の終了を待ってもらう
- **何か** — シャットダウン・サインアウトのとき、Windows はまず全部のウィンドウに「終わってよいか」(`WM_QUERYENDSESSION`) を聞く。未保存の変更があれば FALSE を返して待ってもらい、`ShutdownBlockReasonCreate` で渡した文 (「保存されていない変更があります」) を Windows の「アプリが終了を妨げています」の画面に出す。そのあいだにエディターで保存するか聞く
- **なぜそれか** — 聞かないと、閉じるときの確認を通らずに変更が消える。それでもユーザーが「強制的に」を選んだときは `WM_ENDSESSION` が来るので、すぐ終われるもの (配置) だけ保存する
- **どこ** — `ScreenWindow::OnQueryEndSession` / `OnEndSession`、`EditorScreen` の同じ名前の関数

### 開いているプロジェクトの印 (ファイルのロック)
- **何か** — 同じプロジェクトを 2 つの RM Engine で開かないための印。プロジェクトの横に `<名前>.rmpf.lock` を「ほかの誰とも共有しない」形で開いておく (`CreateFileW` の共有モード 0)。2 つ目が開こうとすると Windows が「共有違反」(`ERROR_SHARING_VIOLATION`) で断るので、開いていると分かる
- **なぜそれか** — `FILE_FLAG_DELETE_ON_CLOSE` を付けると、閉じたときにファイルが消える。アプリが落ちても Windows が持ち物を閉じるので、印が残って「ずっと開けない」にならない (中身に「開いている」と書くだけのやり方だと、落ちたときに残る)
- **どこ** — `platform::FileLock` (`src/platform/FileLock.*`)、`App::OpenProjectNow`、Hub の名前の変更

### 文字コード: UTF-8 と UTF-16
- **何に使っているか** — データの文字は UTF-8 の `std::string`。Windows と DirectWrite に渡すときだけ UTF-16 (`std::wstring`) に変える
- **なぜそれか** — ファイル (JSON) と相性がよく、変える場所を 1 か所 (`base/Utf.h`) に決めておけば文字化けの原因を探しやすい。manifest で exe の文字コードも UTF-8 にしている

## 4. UI の作り方

### 自作の即時モード UI (ImGui は使わない)
- **何か** — 「即時モード」= 毎回の描画で「ボタンをここに描く。押されたら true」とコードで書く UI の作り方。部品の状態をあらかじめ組み立てて持っておく (保持モード) のではなく、毎回描くコードがそのまま UI になる
- **何に使っているか** — Hub とエディターの画面全部
- **なぜそれか** — 書く量が少なく、データと画面がずれない。ImGui (有名な即時モード UI) は使わないとユーザーが決めたので、土台から自作した
- **工夫**
  - 何も起きていないときは描かない (入力・大きさの変化・タイマーがあったときだけ描く) → CPU を使わない
  - 部品は文字列の ID (ハッシュ) で見分ける。前のエンジンでは番号で見分けていて、番号がぶつかる不具合があった
  - 土台 (`src/ui`) は色を持たない。見た目 (`src/editor/widgets` の Theme) と分けたので、ゲームの UI を同じ土台で作っても、エディターの色が混ざらない
  - メニューや一覧はフレームの最後に描く (オーバーレイ)。パネルの端で切れない
- **どこ** — `src/ui/Context.*`、`src/editor/widgets/*`

### 部品の集まり (ImGui のように使い回す)
- **何か** — ボタン・行・タブ・見出し・印・箱を 1 つずつ関数にしたもの。画面のコードは「ここにボタン」と呼ぶだけで、押されたかどうかが返る (ImGui と同じ使い方。ImGui そのものは使わない)
- **なぜそれか** — 前は画面ごとに四角を塗っていて、見た目を変えるには全部の画面を直す必要があった。部品に集めると、1 か所直せば全部変わる
- **どこ** — `src/editor/widgets/Widgets.*`

### グラデーションと影 (Direct2D)
- **何か** — 単色の四角を、上が少し明るく下が少し暗い**縦のグラデーション**にして、光が上から当たっているように見せる。色は元のパレットの色を白や黒に少し混ぜて作るので、色合いは変わらない (`Shade` = 白か黒へ何割か寄せる計算)
- **どう作ったか** — Direct2D の `ID2D1LinearGradientBrush`。色の組ごとにブラシを 1 つ作って覚えておき、描く四角に合わせて始点と終点だけ動かす (毎回作ると遅い)
- **影** — 本物のぼかし (ガウスぼかし) は重いので、少しずつ広く薄くした角丸を 4 枚重ねて、ぼけた影に見せている
- **印** — ×・⋯・▾ などを文字 (フォント) ではなく線と点で描く。文字だと位置がフォント次第でずれる (「…」が下に寄る) が、線ならいつも真ん中
- **どこ** — `src/ui/Painter.cpp` (`FillRoundRectGradient` / `Shadow`)、`src/editor/widgets/Theme.h` (`Raised` / `Gentle` / `Sunken` / `AccentOf`)

### 角ごとに丸さの違う四角と、色が変わる線 (パスジオメトリ)
- **何か** — くっついたパネルの角は四角、外側の角だけ丸くするため、**角ごとに半径の違う四角**を描く。Direct2D の角丸は 4 つの角が同じ丸さしか描けないので、形を自分で組み立てる
- **どう作ったか** — `ID2D1PathGeometry` (パス = 線と弧をつないだ形)。辺は直線 (`AddLine`)、丸い角は 4 分の 1 の円弧 (`AddArc`)、半径 0 の角は弧を飛ばすだけ。できた形を塗る (`FillGeometry`) か、線で縁取る (`DrawGeometry`)
- **縁の線** — 外側の暗い線はパネルの 1 ドット外に引く。パネルのあいだを 1 ドットあけると、両側のパネルの外側の線が同じ所に重なって、区切りがちょうど 1 本になる。内側の明るい線はグラデーションのブラシで引くので、上が明るく下が薄い
- **どこ** — `src/ui/Painter.cpp` (`RoundRectPath` / `FillRoundRectGradient(Corners)` / `StrokeRoundRectGradient`)、`src/editor/widgets/Widgets.cpp` (`DrawPanelFrame`)、`src/editor/dock/DockSpace.cpp` (どの角が外側かを決める)

### 線と曲線で形を描く (ベジェ曲線と回転)
- **何か** — 「桜」テーマの飾りの花を、画像ではなく**線と曲線の組み合わせ (パス)** で描く。画像と違って、どの大きさ・どの画面の細かさでもぼやけず、色もテーマの色で塗れる
- **どう作ったか** — 花びら 1 枚を、中心の近くの丸い先 → いちばん太い所 → 先の 2 つのとがり → 切れ込み、と**3 次ベジェ曲線** (始点・終点と 2 つの「引っ張る点」で決まる曲線) と直線でなぞる。もらった絵から寸法を測った。それを 72 度ずつ回して 5 枚にし、全体を 10 度回す
- **回転の式** — 画面は下向きが y の正なので、見た目で反時計回りに θ 回すのは x' = x cosθ + y sinθ、y' = y cosθ − x sinθ
- **分けたこと** — 形を作る計算 (`ornament::Sakura`) は描画を知らない純粋なコードでテストがある。描くのは `Painter::FillPath` (Direct2D の `ID2D1PathGeometry` に `AddBezier` / `AddLine` で写して塗る)
- **よけるところ** — (前の版) シーンビューとゲームビューの四角を形から切り取っていた (Direct2D の `CombineWithGeometry` の「引き算」)。飾りをいつも背景に描くようになって要らなくなり、外した (下の「テーマパック」)
- **どこ** — `src/ui/Path.h` (形のデータ)、`src/ui/Painter.cpp` (`FillPath`)、`plugins/rm_engine/theme_seasons/editor/Ornament.*` (桜の形)

### 背景に合わせて白か黒を選ぶ (輝度とコントラスト比) と、絵を 1 色で塗る (Direct2D の効果)
- **何か** — Hub のロゴは白 1 色の絵。明るいテーマでは見えなくなるので、左の欄の色が暗ければ白、明るければ黒で描く
- **白か黒かの決め方** — 色の「見た目の明るさ」(相対輝度: 赤・緑・青を、人の目の感じ方の重み 0.2126 / 0.7152 / 0.0722 で足す。色の値はその前にガンマを外す) を出し、白との**コントラスト比**と黒とのコントラスト比 (Web のアクセシビリティの基準 WCAG と同じ式) の大きい方を選ぶ。テーマを足しても自動で合う (`theme::InkOn`。テストあり)
- **1 色で塗る** — Direct2D の**効果** (エフェクト) の 1 つ、カラーマトリックス (`CLSID_D2D1ColorMatrix`)。色を「r, g, b, a に行列を掛ける」計算で変える。色の部分を決まった色にして、透明さ (アルファ) だけを残すと、絵の形をした 1 色の絵になる。縮めるときはきれいな補間 (`HIGH_QUALITY_CUBIC`) で描く。効果の識別子のために `dxguid.lib` をリンクした
- **どこ** — `src/editor/widgets/Theme.h` (`Luminance` / `InkOn`)、`src/ui/Painter.cpp` (`ImageTinted`)、`src/editor/hub/HubScreen.cpp` (`DrawSidebar`)

### 季節の絵 (図形を重ねて 1 つの影にする・決まった乱数)
- **何か** — 季節のテーマの絵 (桜の木・太陽・浜辺・砂の城・椛・雪の結晶・降る雪・つらら・積もった雪など) を、画像ではなく線と曲線のパスで描く
- **図形を重ねて 1 つの影に** — 桜の木の花は何十個もの円を重ねて作る。パスの塗り方には「交互 (alternate)」と「巻き数 (winding)」があり、交互だと 2 つ重なった所が抜けて穴になる。巻き数で塗り、図形を全部同じ向き (時計回り) に作ると、重なった所も塗られて 1 つの影になる。向きは「符号付き面積」(頂点を順に掛け合わせた和) の正負で分かるので、逆向きの多角形は裏返してから足す
- **円と楕円** — 3 次ベジェ曲線 4 本で円になる (制御点を半径の 0.5523 倍の所に置く)
- **決まった乱数** — 花びらや葉を「ばらばらに」置くのに、種 (シード) の決まった小さな乱数 (xorshift32) を使う。毎フレーム同じ数が出るので、描き直しても絵が動かない
- **どこ** — `plugins/rm_engine/theme_seasons/editor/Ornament.*` (形。テストあり)、`Seasons.cpp` (季節ごとの絵・積もる雪)、`src/ui/Painter.cpp` (`FillPath` の winding)

### 数をドラッグで変える (無限に動かせるスライダー)
- **何か** — 数の欄の名前を左右にドラッグすると数が変わる (Unity・Blender と同じ)
- **どうやって** — ドラッグ中はカーソルを隠して最初の位置に戻し続け、マウスが「動いた量」だけを足していく (シーンビューのカメラと同じ仕組み。画面の端で止まらない)。足した量 × 速さ + 始めの値 = 今の値。速さは始めた時の値で決める (大きい数ほど速い: max(1, √|値|) × 0.03)。Shift で速く、Alt で遅く
- **どこ** — `src/editor/inspector/Inspector.cpp` (`Scrub`)

### Undo のまとめ (打つたびに反映しても、Undo は 1 回分)
- **何か** — インスペクターの欄は打つたびに値が変わる。そのままだと「1」「12」「123」がそれぞれ Undo 1 回分になるので、1 つの欄に入っている間の編集は 1 つにまとめる
- **どうやって** — 欄に入るたびに番号 (まとめの鍵) を作り、編集にその番号を付ける。履歴に積むとき、一番新しい記録が同じ番号・同じ欄なら、新しい記録は作らずに「どこまで変わったか」だけを書き換える (Qt の `mergeWith` と同じ考え)。何かを Undo した後はまとめない (やり直しの記録が消えるので)。打ってから Esc で元に戻し、結局何も変わらなかったら記録ごと消す
- **ワールドの値を打つ** — 見せているのは親を含めた値なので、打った値を「親から見た値」に直してから記録する。位置は親のワールド行列の逆行列を掛ける。回転は親の回転を打ち消す。大きさは親がその軸をどれだけ伸ばしているかで割る。打った所だけを変える (位置を打って回転が少しずれる、ということがない)
- **どこ** — `src/core/UndoHistory.*` (`MergeWith`)、`src/core/reflect/FieldCommand.*`、`src/editor/inspector/Inspector.cpp`、`plugins/rm_engine/space3d/runtime/Transform.cpp` (`FromWorld`)

### ギズモ (3D の物をマウスでつかんで動かす・回す・大きさを変える)
- **何か** — 3D ツールでおなじみの、選んだ物に出る矢印・輪・箱。つかんでドラッグすると物が動く。Unity と同じ操作 (W / E / R・X でローカル / ワールド・Ctrl で刻む)
- **マウスの点 → 3D の線 (レイ)** — 画面の点を、カメラの行列の逆行列で「手前の面」と「奥の面」の 2 点に戻すと、その 2 点を通る線がマウスの指している 3D の線になる
- **矢印で動かす** — 「マウスの線」と「矢印の軸の線」の、一番近づく所を出す (2 本の線の最近点。内積の式 1 つ)。つかんだときからそこがどれだけ進んだかが動いた量
- **面の四角で動かす** — 「マウスの線」と「面」の交わる点 (レイと平面の交点)
- **輪で回す** — 輪をつかんだ点で、輪が前に進む向き (軸 × 中心からの向き の外積) を画面に写す。マウスがその向きに動いた長さ ÷ 輪の半径 (ピクセル) = 回った角度 (ラジアン)。輪を真横から見ていても回せる
- **回転を数字に戻す** — 回した結果は行列 (軸のまわりの回転 = ロドリゲスの式) で計算し、インスペクターに出すオイラー角 (X → Y → Z の角度) に戻す。同じ向きを表す角度の組は 2 つ (と 360 度ずつずらしたもの) あるので、**いま出ている数字に一番近い組**を選ぶ (179 度 → 181 度が -179 度に飛ばない)。真上・真下を向いたとき (ジンバルロック) は Z を変えずに X だけで表す
- **親がいるとき** — 動いた量・回す軸はワールドで計算し、親のワールド行列の逆行列で「親の中の量」に直してから Transform に足す (Transform は親から見た値なので)
- **いつも同じ大きさに見せる** — カメラからの奥行きに比例して大きくする (1 ピクセルが何 m か = 2 × 奥行き × tan(視野角 / 2) ÷ 画面の高さ)
- **Undo** — ドラッグ中は値を直接変え、離したときに「前の値 → 後の値」を 1 つの Undo (いくつも選んでいればまとめて 1 つ) にして積む
- **どこ** — `plugins/rm_engine/space3d/editor/Gizmo.*` (計算。テストあり)、`plugins/rm_engine/space3d/runtime/Transform.cpp` (回転の行列と角度)、`plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp` (描く・ドラッグ)

### ドッキング (木で配置を持つ)
- **何か** — パネルをタブにしたり、分割したり、別のウィンドウに出したりする仕組み
- **どう作ったか** — 配置を「木」で持つ。節は「分割 (向きと比率)」か「葉 (タブの並び)」。パネルを動かす = 木から抜く → 入れる → 空いた所をたたむ。この木の操作は描画から切り離した純粋なコードで、テストがある
- **ウィンドウをまたぐ** — ドラッグ中、マウスの下にあるウィンドウを Windows に聞いて (`WindowFromPoint` に相当する処理)、そのウィンドウに目印を出す
- **保存** — 配置はプロジェクトの `UserSettings/Layout.json` に JSON で
- **名前を付けた配置** — 今の木を JSON にして名前と一緒に一覧に入れておき、選んだら JSON から木を作り直す (消えたパネルは `Sanitize` で外す)。名前などの項目はリフレクション (`RM_STRUCT`) で保存し、知らないキーは書き戻す。どのプロジェクトでも使う「共通の配置」は、ユーザーごとの設定の場所 (Windows の「移動プロファイル」の AppData = `%APPDATA%`。`SHGetKnownFolderPath(FOLDERID_RoamingAppData)`) に同じ形で置く
- **入りきらないタブの列** — タブの幅を全部足した長さと、見える幅から「どれだけずらすか」(スクロール量) を計算する。表に出したタブが見えるように動かす量・‹ › で次のタブの端まで動かす量・落とした所が何番目かも、画面から切り離した計算 (テストあり)。見える所の外は「切り抜き (クリップ)」で描かず、押せない
- **どこ** — `src/editor/dock/DockLayout.*` (木とタブの列の計算)、`NamedLayouts.*` (名前を付けた配置)、`DockSpace.*` (描画と入力)

### 木の表示 (階層)
- **何か** — 開く・閉じる・選ぶ (Ctrl / Shift)・ドラッグで並べ替え・名前の変更・検索 ができる木の表示
- **どう作ったか** — 核は木の見せ方だけを持ち、何を並べるかはソフトが決める (インターフェース `tree::Source`)。「見える行」「選択」「どこに落とすか」は純粋な計算でテストがある
- **どこ** — `src/editor/tree/*`

### パネルをまたぐドラッグ (ドラッグ & ドロップ)
- **何か** — アセットのパネルや階層の行をつかんで、インスペクターの参照の欄に落とすと入る
- **どう作ったか** — マウスは 1 つなので、運んでいる物 (種類と ID) を置く場所をプログラムに 1 つだけ作った (`w::DragThing`)。つかんだ側は運んでいる間そこに置き、受ける側 (`w::DropTarget`) はマウスが上にあれば枠を光らせ、ボタンが離されたフレームで受け取る。置き場はフレームの最後に片付ける (後から描かれるパネルも「離した」を見られる)。Windows の OLE のドラッグ & ドロップは使っていない (エディターの中だけで済むので)
- **別のウィンドウへ** — マウスを捕まえているのはドラッグを始めたウィンドウだけなので、そのウィンドウが「マウスの下にあるのは自分の仲間のウィンドウか」(`WindowFromPoint` に近い `TopLevelWindowAt`) を調べ、その窓の座標 (`ScreenToClient` ÷ DPI の倍率) を教えて描き直させる。教えられた窓の欄は、その点で光り、離したと教えられたら受け取る
- **どこ** — `src/editor/widgets/Widgets.*`、`src/editor/tree/TreeView.cpp` (`Source::DragOut`)、`src/editor/inspector/Inspector.cpp` (`DrawRef`)

### 色のテーマ (黒・白・PC に合わせる)
- **何か** — 画面の色を 2 つの組 (黒と白) で持ち、切り替える仕組み
- **どう作ったか** — 色は全部 `theme::` の変数を通して使うので、変数の中身を入れ替えるだけで全部の画面が変わる。タイトルバーは DWM の `DWMWA_USE_IMMERSIVE_DARK_MODE` / `DWMWA_CAPTION_COLOR` で合わせる
- **PC に合わせる** — Windows の設定はレジストリ `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` の `AppsUseLightTheme` にある。Windows は設定が変わると全部のウィンドウに `WM_SETTINGCHANGE` ("ImmersiveColorSet") を送るので、それを受けて読み直す
- **どこ** — `src/editor/widgets/Theme.h`、`src/platform/Window.cpp` (`SetCaption`)、`src/platform/Shell.cpp` (`SystemPrefersLight`)

### 多言語化 (日本語の文を鍵にした翻訳表)
- **何か** — 画面の文字を言語に合わせて出し分ける仕組み (i18n)。gettext という有名な仕組みと同じ考え方で、**元の言語 (日本語) の文そのものを鍵**にして、英語の表 (JSON) を引く
- **良い点** — コードを読めば何が出るか分かる (番号や英字の ID にしない)。英語が無い文は日本語のまま出るので、訳し忘れても画面が壊れない
- **訳し忘れを止める** — ビルドのたびに `tools/check_lang.ps1` がソースを読み、`Tr(L"…")` などの文と、リフレクションの項目名に英語があるかを調べる。`{}` (std::format の差し込み) の数が違っても失敗にする
- **std::vformat** — 訳した文に値を差し込むのは、実行中に決まる書式で `std::vformat` を使う (書式が合わなければ日本語の書式に戻る)
- **どこ** — `src/editor/lang/*`、`resources/lang/en.json`、`plugins/*/*/lang/en.json`、`tools/check_lang.ps1`

### 自動保存 (タイマー)
- **何か** — Windows のタイマー (`SetTimer` → `WM_TIMER`) で 15 秒ごとに起き、未保存の変更が決めた時間たっていれば保存する
- **工夫** — 入力中・ドラッグ中 (`GetKeyState` でマウスのボタン)・ダイアログ中は保存しない。何も起きていないときは描かない作り (CPU 0%) を崩さないよう、タイマーは描画せずに見るだけ
- **どこ** — `src/editor/shell/EditorScreen.cpp` (`OnTimer`)

## 5. データと保存

### 自作の JSON
- **何か** — 人が読める文字のデータ形式。RM Engine の保存ファイル (`.rmpf`・`Layout.json`・`hub.json`・`plugin.json`) は全部 JSON
- **なぜ自作か** — **キーの順番を保ったまま読み書きし、知らないキーも捨てずに書き戻す**ため。新しい版で保存したファイルを古い版で開いて保存しても、データが消えない。読み書きを繰り返してもバイト単位で同じになる (テストあり)
- **大きなオブジェクト** — キーの順番を保つためにキーは並び (配列) で持つ。キーを探すのは小さいオブジェクト (16 未満) では頭から順に、大きいものはハッシュ表の索引 (必要になったときに作り、`Set` で足していく。中身はただの写し: 値をコピー・移動しても付いていかない) で。読み込みで重なったキーを確かめるのも同じ索引なので、100 万キーでも一直線 (前はキーごとに頭から探して 2 乗)
- **どこ** — `src/base/Json.*`

### リフレクションとコード生成 (rmgen)
- **何か** — リフレクション = プログラムが自分のデータの形 (フィールドの名前・型) を知っている仕組み。C++ には無いので、ヘッダーを読んで表を作る小さなツール (rmgen) を自作した
- **何に使っているか** — データの型を 1 か所に書くだけで、保存・読み込み・インスペクター (編集画面)・比較・Undo・値の範囲の制限 がそこから出る
  ```cpp
  RM_STRUCT(Label="ゲームの設定")
  struct GameSettings {
      RM_PROPERTY(Edit, Label="目標 FPS", Min=1, Max=240) int targetFps = 60;
  };
  ```
- **仕組み** — `RM_PROPERTY` などは中身が空のマクロ (目印)。ビルドの最初に rmgen がヘッダーを読み、型の表 (`TypeDesc`) を C++ のコードとして書き出す。保存やインスペクターは、どの型でもこの表を辿る共通の関数 1 本ずつ
- **書き忘れを止める** — 目印の無いフィールドは rmgen がエラー (`error RM0001` とヘッダーの行・列) にする。ヘッダーを変えて rmgen を通さないと、生成したコードの `static_assert` (コンパイル時の検査) が「フィールドの数」(集成体のメンバーの数を C++20 の `requires` で数える) と名前・型の食い違いで止める
- **なぜそれか** — 前のエンジンでは保存・読み込み・編集画面を型ごとに手で書き、書き忘れやずれで不具合が出た。1 か所に書けばずれようがない
- **どこ** — `src/core/reflect/*`、`tools/rmgen/*`、`src/RM.Reflect.targets` (MSBuild に組み込む)

### アセットの ID (GUID と .meta)
- **何か** — 素材のファイル 1 つ 1 つに、動かしても名前を変えても変わらない番号 (GUID = 128 ビットの乱数を 32 文字の 16 進で) を付け、ファイルの横の小さな JSON (`<名前>.meta`) に書いておく。Unity と同じ形
- **何に使っているか** — データが素材を指すとき (`AssetRef`) はパスではなくこの ID を持つ。ファイルを動かす・名前を変えるときは `.meta` も一緒に動かすので、指した先が外れない
- **エディターの外で動かされたとき** — フォルダを読み直すたびに「`.meta` が置き去りになった物」と「`.meta` の無い新しい物」を比べ、同じ名前で 1 つだけ (動かした)・同じフォルダで同じ拡張子で 1 つずつ (名前を変えた) なら同じ物とみなして ID を引き継ぐ。どちらか分からないときは新しい ID (間違えてつなぐより安全)。この判断は純粋な関数 (`Reconcile`) でテストがある
- **乱数** — `std::random_device` で種をまいた `std::mt19937_64` (64 ビットのメルセンヌ・ツイスタ) を 2 回引く
- **どこ** — `src/core/asset/*` (ゲームにも入る: ゲームは `.meta` を読んで ID からファイルを探す)、`src/base/Ref.h` (参照の型)

### Undo (コマンドパターン)
- **何か** — 「やったこと」を `Do` / `Undo` を持つ小さなオブジェクト (コマンド) にして積んでおく作り方
- **何に使っているか** — 編集の取り消しとやり直し。**Undo に積んだ = 未保存** と決めているので、編集が保存されずに消えることがない
- **工夫** — どの型のどのフィールドの変更も 1 種類のコマンド (`SetFieldCommand`、リフレクションで値を出し入れ) で表す。シーンの形の変更 (作る・消す・動かす) は前後の状態を持つコマンド。Undo の途中で新しいコマンドを積もうとしたら断る (前のエンジンの不具合の再発防止)
- **どこ** — `src/core/UndoHistory.*`、`src/core/reflect/FieldCommand.*`

### 型を消した値 (type erasure)
- **何か** — 「何の型か」をコンパイル時に決めず、実行中に型の表 (`TypeDesc`) を見て値を作る・写す・壊す入れ物
- **何に使っているか** — エンティティの部品 (コンポーネント)。ゲーム制作は Transform という型を知らないが、型の表があれば Transform の値を持てる
- **どう作ったか** — 型の表の大きさでメモリを取り、表の construct (既定値で作る)・copy・destruct を呼ぶ。C++ の「5 つの特別な関数」(コピー・移動・代入・デストラクタ) をきちんと書いて、ふつうの値と同じに使える
- **どこ** — `src/core/reflect/Object.*`

### 整合性の確認 (SHA-256)
- **何か** — ファイルの中身から 32 バイトの「指紋」(ハッシュ) を作る計算 SHA-256 で、ファイルが壊れていないか・入れ替わっていないかを確かめる。Steam の「ゲームファイルの整合性を確認」と同じ考え方
- **どう作ったか** — ビルドの最後に PowerShell の `Get-FileHash` でエンジンのファイルの一覧と指紋を JSON に書く。確認のときは Windows の暗号の仕組み BCrypt (`BCryptHashData`) で指紋を計り直して比べる
- **限界** — 一覧そのものに署名が無いので、悪意のある書き換えは防げない (壊れた・欠けた・古いを見つけるためのもの)
- **どこ** — `tools/make_filelist.ps1`、`src/editor/app/Integrity.*`、`src/platform/Shell.cpp` (`Sha256File`)

### 埋め込みリソース
- **何か** — 画像や JSON を exe の中に入れておく Windows の仕組み (`.rc` ファイルの `RCDATA`)。ファイルを無くす心配が無い
- **何に使っているか** — Hub のロゴ、アップデート情報 (`resources/updates.json`)
- **どこ** — `resources/app.rc`、`platform::ResourceBytes`

### 大きなデータを別のファイルに分け、変わった物だけ書く (シーンのファイル)
- **何か** — 1 つの大きな保存ファイルに全部を入れず、大きくなる部分 (ゲームのシーン) を 1 つずつ別のファイルにする作り。元のファイル (`.rmpf`) には、その部分を指す ID の一覧だけを残す。Unity の `.unity` (シーン) と `ProjectSettings` の分け方と同じ
- **何に使っているか** — ゲームのシーンを `Assets/Scenes/*.rmscene` に。`.rmpf` は 256 MB の上限に近づかず、保存のたびに全部を書き直さない
- **変わった物だけ書く工夫** — 書こうとする中身の「印」(FNV-1a という簡単なハッシュ関数で作る 64 ビットの数) を、ファイルを読んだとき・書いたときの印と比べ、同じなら書かない。編集の回数ではなく中身で比べるので、Undo で元に戻したときも書かない。FNV-1a は 1 バイトずつ「XOR して素数を掛ける」だけの速い関数 (暗号には使えないが、変わったかどうかを見るには十分)
- **壊さない順番** — 分けたファイルを全部書いてから、それを指す `.rmpf` を書く (`.rmpf` がまだ無いファイルを指す瞬間が無い)。どれも `.tmp` に書いてから置き換える。新しいファイルは ID の `.meta` を先に書く
- **前の形からの移し替え** — 前の版の `.rmpf` (シーンが中にある) も読み、次の保存で分ける。分ける前のファイルは `.before-scenes.bak` として 1 回だけ残す
- **どこ** — `plugins/rm_engine/game_production/runtime/SceneFile.*` (形・印・何を書くかの計算。純粋でテストあり)、`src/editor/plugin/Software.h` (`ProjectFileWrite`)、`src/editor/shell/EditorScreen.cpp` (`Save`)

### 知らないデータを捨てない
- 新しい版のファイルや、プラグインが無い状態で開いたファイルでも、分からないキー・分からない選択肢の名前を覚えておいて、保存のときにそのまま書き戻す (`reflect::Unknowns`)
- 選択肢 (列挙) は番号ではなく**名前**で保存する。選択肢の順番を変えても古いファイルの意味が変わらない

## 6. プラグイン

### 静的リンクのプラグイン
- **何か** — 機能 (ソフト) をプラグインとして分けて作る仕組み。コードは exe に全部入れておき (静的リンク)、「インストールしたものだけ有効にする」
- **なぜそれか** — DLL を後から読み込む方式より簡単で安全 (読み込み失敗やバージョン違いが起きない)。プラグインを足すときは `plugins/<作者>/<名前>/` にフォルダを足すだけ (プロジェクトファイルはワイルドカードで全部拾う)
- **plugin.json** — プラグインの ID・名前・前提 (requires) を書く。コードの中の ID と照らし合わせ、食い違えば使わない
- **前提の解決** — 前提のプラグインを先に並べる (トポロジカルソート)、輪になっていないか・欠けていないかを調べる。純粋な計算でテストあり
- **柵** — 核 (`src/`) はプラグインを知らない。プラグインは `requires` に書いたものしか `#include` できない。ゲームに入る部分 (`runtime/`) はエディターの部分 (`editor/`) を使えない。全部 `check_layers.ps1` が調べる
- **どこ** — `src/editor/plugin/*`、`plugins/*`

### つなぎプラグイン (前提の向きを 1 方向にする)
- **何か** — 2 つのプラグインの「両方を知らないと作れない部分」だけを、両方を前提にした 3 つ目のプラグインに切り出す作り方
- **何に使っているか** — ゲーム制作は 3D も 2D も知らずに作り、「ゲーム制作 × 3D」が 3D 空間の Transform をゲームの部品として渡す。2D のゲームに 3D の部品が入らない
- **なぜそれか** — ゲーム制作が 3D 空間を直接読むと、使わないゲームにも 3D が入る。つなぎの方からだけ矢印を向けると、前提が輪にならない
- **決まり** — `plugin.json` に `needsConnector` (つなぎが要る) と `connectorFor` (誰のつなぎか)。つなぎが 1 つも使えないと、つなぎが要る側は使えない。つなぎは要るものがそろうと自動で入る
- **どこ** — `src/editor/plugin/PluginManifest.cpp`、`plugins/rm_engine/game_x_3d/`

### テーマパック (ファイルだけのプラグイン) と、背景に描く飾り
- **何か** — 色のテーマを、JSON のファイル (`themes/*.json`) を持つプラグインとして足す作り。コードの無いプラグインもふつうに「インストール」「削除」できる。絵 (季節の飾り) が要るパックは、その絵を描く関数を差し出しの口に渡す
- **背景に描く工夫** — 飾りをウィンドウの最後に重ねると文字にかぶる。そこで、ウィンドウの地・パネルの地・帯の地を塗るたびに、**ウィンドウ全体の同じ絵をその四角で切り取って (クリップして) 描き直す**。どこでも絵は地のすぐ上・中身のすぐ下になる。何度も描くので、ウィンドウの大きさごとに作った形を覚えておく (キャッシュ)
- **どこ** — `src/editor/widgets/ThemeFile.*` (読み込み)、`Widgets.cpp` (`DrawBackdrop` / `DrawBackdropOn`)、`src/editor/app/App.cpp` (`LoadThemes`)、`plugins/rm_engine/theme_*`

### テンプレート (データで書くひな形と、パスから作る木)
- **何か** — 新しいプロジェクトの最初の中身 (要るプラグイン・最初に開くソフト・最初のシーン・最初の配置) を、コードではなく JSON のファイル (`template.json`) に書く作り。Unity Hub の「3D / 2D を選んで作る」と同じ役目。木は、ファイルごとに書いた「木の場所」(`"path": ["game", "3d"]`) を並べて核が組み立てる (パスの前の部分が枝。ファイルのフォルダ分けとは関係ない)
- **何に使っているか** — Hub の新規作成のダイアログ。「白紙」「ゲーム」「3D のゲーム」「2D のゲーム」。枝を選ぶとその下の全部のテンプレートが使うプラグインを入れる (前提とつなぎは、プラグインのインストールの計画をそのまま使う)。Hub のプラグイン一覧の「ソフトで絞る」も、この木の一番上の枝から決める
- **なぜそれか** — コードにすると、そのプラグインが入って動いていないとテンプレートが見えない。データなら、入っていないプラグインのテンプレートも木に出して「インストールしますか」と訊ける。木を別のファイルに書かないので、テンプレートを足すだけで木が育つ (同じことを 2 か所に書かない)
- **工夫** — 核は中身の意味を知らず、`project` のキーを新しい `.rmpf` に、`userSettings` を `Layout.json` に写すだけ。リポジトリのテンプレートの最初のシーンは、テストで実際にシーンとして読んで警告が出ないことを確かめる (書き間違いを CI で止める)
- **どこ** — `src/editor/project/Templates.*` (読み方・木・計算。純粋でテストあり)、`src/editor/plugin/Plugins.cpp` (`LoadTemplates`)、`src/editor/hub/HubScreen.cpp` (ダイアログ)、`plugins/rm_engine/*/templates/`

### 書き出したゲームを作る (静的ライブラリのリンク・生成する初期化のファイル)
- **何か** — エンジンの核と各プラグインのゲームに入る部分を、ビルドのたびに**静的ライブラリ** (`.lib` = .obj を束ねたもの) にしておき、書き出すときにそのゲームが使うものだけを**リンカ** (`link.exe`) でつないで `<ゲームの名前>.exe` を作る
- **何に使っているか** — ゲームの書き出し。2D のゲームには 3D の部分が入らない (exe が小さく、使っていない物が入らない)
- **罠と工夫** — リンカは静的ライブラリの .obj のうち、**名前を呼ばれた物だけ**を入れる。「起動のときに自分で登録する」作りだと、誰も名前を呼ばないので登録ごと捨てられる。そこで書き出しのたびに、使うプラグインの登録関数と反映する型の名前を並べるだけの小さな `main.cpp` を生成してコンパイルし、一緒にリンクする (名前を呼ぶので必ず入る)。登録関数は C の名前 (`extern "C"`) にして、生成したファイルがヘッダーを読まずに呼べるようにした
- **どこ** — `src/RMGameKit.vcxproj` と `tools/make_gamekit.ps1` (ライブラリを作る)、`src/editor/export/ExportPlan.*` (生成)・`Exporter.*` (cl / rc / link を呼ぶ)、`src/core/RuntimeRegistry.h` (`RM_RUNTIME_ENTRY`)

### リソースの埋め込み (アイコンとゲームの名前)
- **何か** — exe の中にアイコンや文字 (ファイルの説明・製品名) を入れておく Windows の仕組み。`.rc` (リソーススクリプト) に書き、`rc.exe` で `.res` にして一緒にリンクする
- **何に使っているか** — 書き出したゲームのアイコン (エクスプローラーとタスクバー) と「プロパティ → 詳細」の名前。作るときに入れるので、前のエンジンのような「コピーした exe のアイコンを後から書き換える」処理が要らない
- **工夫** — 日本語の名前は `rc /c65001` (UTF-8 として読ませる)。アイコンは PNG をそのまま中に入れた `.ico` (Windows Vista から読める形。変換しない)
- **どこ** — `src/editor/export/ExportPlan.cpp` (`GameResourceSource`・`IcoFromPng`)

### アプリごとの C++ ランタイム (app-local deployment)
- **何か** — C++ のプログラムが使うランタイムの DLL (`vcruntime140.dll` など) を、PC に「再頒布パッケージ」を入れてもらう代わりに、exe と同じフォルダに置いて配る方法。Microsoft が認めている配り方
- **何に使っているか** — 書き出したゲームとスクリプトの DLL (`/MD`) が、何も入っていない PC で動くように。Visual Studio の `VC\Redist\MSVC\<版>\x64\Microsoft.VC*.CRT\` から写す。エンジン自体は `/MT` (ランタイムを exe に静的に入れる) なので、スクリプトが無ければ DLL が無くても動く
- **どこ** — `src/editor/export/Exporter.cpp` (`RuntimeDlls`)、`src/RM.Common.props` (`RmCrt`: どのランタイムかを 1 か所に)

### Visual Studio を外から使う (vswhere と vcvars)
- **何か** — `vswhere.exe` は入っている Visual Studio の場所を教えてくれる Microsoft のツール。`vcvars64.bat` はコンパイラやリンカの場所・ライブラリの場所を環境変数に入れるバッチファイル
- **何に使っているか** — 書き出しで `cl` / `rc` / `link` を起動する。バッチを 1 回走らせて `set` で環境変数を受け取り、その環境で各ツールを直に起動する (日本語のパスもそのまま扱える)。ツールのメッセージは `VSLANG=1033` で英語にして受け取る (コードページの文字化けを避ける)
- **どこ** — `src/editor/export/Exporter.cpp`、`src/platform/Process.*` (別のプログラムを起動して出力を読む: `CreateProcessW` とパイプ)

### .rmpak (書き出したゲームのアセットを 1 つに詰める) と AES
- **何か** — 書き出したゲームが使うファイル (シーン・画像・設定) を 1 つのファイルにまとめた RM Engine 独自の形。頭に目次の場所、後ろに目次 (パスと場所と大きさと印)
- **暗号化** — 中身と目次を **AES-256** (世界中で使われている標準の暗号) の **CTR モード** で暗号化する。Windows に入っている暗号の機能 **CNG (BCrypt)** を使い、外のコードは入れない。CTR は「カウンターを AES で暗号化した列」と XOR する作り: 暗号化と復号が同じ計算、ファイルの好きな所から読める、大きさが変わらない。BCrypt に CTR は無いので、カウンターの並びを ECB で暗号化して作る。正しさは NIST の試験ベクトル (SP 800-38A F.5.5) で確かめている。鍵は「エンジンの秘密の 32 バイト + 書き出しの番号」の SHA-256 (同じゲームを書き出し直すと同じファイル)。今の CPU は AES 専用の命令を持つので、読み込みが遅くなることはほぼ無い
- **★ 正直に: 守れること・守れないこと** — ゲームは遊ぶ人の PC で自分のアセットを読むので、**解くための鍵 (とその作り方) は必ず exe の中にある**。だから、
  - 守れる: フォルダを開いた人・`Game.rmpak` をメモ帳や画像ソフトで開いた人・ファイルを抜き出して別のゲームに使おうとする普通の人。シーンの文字も画像も、そのままでは見えない
  - 守れない: exe を逆アセンブルして鍵の作り方を探す人、ゲームが動いている間のメモリを読む人、画面を撮る人。市販のゲームのデータも同じように抜かれている。**完全に隠す方法は無い**
  - 目標は設計の決めたとおり「普通の人がそのまま取り出せない」まで。本気の相手に対しては、法律 (利用規約・著作権) で守ることになる
- **ほかの工夫** — ファイルごとの印 (FNV-1a) で壊れたら読まない。exe と同じ書き出しの番号でなければ読まない (別の書き出しと混ぜない)。形式の番号 2 (1 は最初の版の簡単な XOR。もう読まない)
- **どこ** — `src/core/pak/Pak.*` (形。暗号は関数で受け取るので純粋なまま。テストあり)、`src/platform/Crypto.*` (AES-CTR・SHA-256・`PakCipher`)

### 差し出しの口 (拡張ポイント)
- **何か** — プラグインが別のプラグインへ物を渡すための、名前の付いた口。渡す側と受け取る側は直接お互いのコードを呼ばず、核の登録簿 (`PluginRegistry`) を通す
- **何に使っているか** — 「ゲーム制作 × 3D」が Transform を `rm_engine.game_production.component` の口に差し出し、ゲーム制作がそこから部品の種類を集める
- **工夫** — 物は `const void*` で預かるが、預けた型 (`typeid`) も覚えておき、違う型として取り出そうとしたら渡さない (型の安全)
- **どこ** — `src/editor/plugin/Software.h` (`Contribute` / `Contributions`)

## 7. テストと品質

- **自作の小さなテストの仕組み** — `RM_TEST(名前) { CHECK(条件); }` で書く。失敗があれば終了コードが 0 以外になり、CI が気づく (`tests/Test.h`)
- **純粋な計算を分けてテストする** — 画面やファイルを使わない部分 (JSON・Undo・ドッキングの木・プラグインの前提・リフレクション・階層・シーン) はテストがある。テストは GPU もファイルも使わない
- **わざと壊して確かめる** — 層の検査は、違反をわざと入れて全部見つかることを確かめた
- **ログ** — `%LOCALAPPDATA%\RM_Engine\Logs\editor.log` に書き、同じものをエディターのコンソールに出す (複数のスレッドから書いても壊れないように `std::mutex`)

## 8. ゲーム制作と 3D 空間・2D 空間のいま

- **シーンとエンティティ** — エンティティは `id`・親の `id`・名前・有効 を持つ (リフレクションで定義)。並びの順 = 兄弟の順。ID は使い回さない。壊れたファイル (同じ ID・無い親・親の輪) は読み込むときに直す
- **どこ** — `plugins/rm_engine/game_production/runtime/Scene.*`

### ECS (エンティティ・コンポーネント・システム) の「C」
- **何か** — ゲームの物 (エンティティ) を、部品 (コンポーネント: 位置・見た目・当たり判定 …) の組み合わせで作る考え方。物の種類ごとにクラスを作る (継承) のではなく、部品を付け外しして作る。S (システム) は部品を持つ物を毎フレーム動かす処理 (下の「S」)
- **何に使っているか** — エンティティは部品を型ごとに 1 つまで持つ (「複数可」の型は何個でも。そのときは「型 + その型の中の何番目」で部品を指す)。インスペクターで足す・外す・並べ替える・値を変える。全部 Undo できる
- **保存** — 部品は型の名前 (C++ の名前) と値で保存。プラグインが無くて使えない部品も、読んだまま書き戻して消さない
- **どこ** — `plugins/rm_engine/game_production/runtime/Components.h`、`Scene.*`

### ECS の「S」(システム) と固定の刻み (fixed timestep)
- **何か** — システム = 部品を持つ物を毎フレーム動かす関数 (例: 「回り続ける」を持つ物の Transform を回す)。部品と同じく**プラグインが差し出す** (`kSystemPoint` に `SystemInfo{名前, 種類, 順番, 関数}`)
- **固定の刻み** — 物理やゲームのルールは、PC の速さで結果が変わらないように**決まった時間 (例: 0.02 秒) ずつ**進める。フレームの時間をためておき (`carry`)、刻み 1 つ分たまるたびに 1 回動かす。速い PC では 0 回のフレームもあり、遅い PC では 1 フレームに何回も動く。止まっていた後の長いフレームで何百回も動かないよう、1 フレームに 8 回まで (残りは捨てる)。見た目 (回転・アニメーション) は「毎フレーム」の種類でフレームの時間を掛けて動かす
- **順番** — 毎フレーム: 固定の刻みのシステムを全部 (刻みの数だけ) → 毎フレームのシステム。種類の中は `order` の小さい順、同じなら差し出された順
- **どこ** — `plugins/rm_engine/game_production/runtime/Systems.*`、「回り続ける」は `plugins/rm_engine/game_x_3d/runtime/Spin.*` (テスト: `tests/TestSystems.cpp`)

### Play (コピーで動かし、止めると戻る)
- **何か** — エディターの中でゲームを動かして見る。Play を押すと**シーンを丸ごとコピー**し、コピーにシステムを掛ける。止めるとコピーを捨てるだけで、元のシーン・Undo の履歴・未保存の印は一度も触られない (Unity の Play モードと同じ考え)
- **どう分けたか** — 核は「Play」を知らない。ソフトが `Software::Tick` (毎フレーム、描く前) で進め、`DrawToolbar` でタブの帯にボタンを出し、`Running()` が真の間は核が帯をアクセントの色にし、Undo / Redo を止める。インスペクターのかたまりには「見せるだけ」(`readOnly`: その間は欄への入力を切る) を足した
- **時間** — 前のフレームからの時間 (`ui::Context::Time` の差。最大 0.25 秒) で進め、動いている間は `RequestAnimation` で次のフレームを頼み続ける
- **どこ** — `plugins/rm_engine/game_production/editor/GameSoftware.cpp`、`src/editor/plugin/Software.h`

### 触った物だけを覚える Undo (記録と復元)
- **何か** — 形を変える操作の前に「この物たちを触る」と言い、その物たちの中身 (ある / ない・並びの中の場所・保存の形の JSON) を操作の前と後で取っておく。Undo / Redo ではその物たちだけを入れ直す。シーン全体の写しを持たないので、大きなシーンでも 1 回分の記憶が小さい (Unity の `Undo.RecordObject` と同じ考え)
- **正しさの守り方** — 「触る」と言い忘れた物があると Undo が正しく戻らない。そこで (1) 開発用の Debug ビルドでは毎回シーン全体も取って比べ、違えば止める (2) 乱数で作った数千回の操作で、1 回ごとに Undo / Redo の後のシーン全体を比べるテスト (ランダムテスト・プロパティベーステストと呼ばれるやり方)
- **場所が合う理由** — 触らなかった物は、操作の前後で並びの中の順が変わらない。触った物を全部取り出してから、覚えた場所の小さい順に入れ直すと、元の並びがそのまま戻る
- **どこ** — `plugins/rm_engine/game_production/runtime/SceneRecord.*`、`Scene::CaptureStates` / `RestoreStates` (テスト: `tests/TestSceneRecord.cpp`)

### C++ スクリプト (DLL・関数テーブル・MSBuild・SEH・ホットリロード)
- **DLL (ダイナミックリンクライブラリ)** — 実行中に読み込めるコードのファイル。ゲームの動き (スクリプト) を DLL にして、エディターが `LoadLibrary` で読み、`GetProcAddress` で関数を探して呼ぶ。エディターを止めずに入れ替えられる。読み込み中の DLL は上書きできないので、ビルドするたびに別の名前 (`Scripts_0007.dll`) にする
- **関数テーブル** — エンジンの機能 (ログ・キー・Transform …) を、関数ポインタを並べた構造体 (`RmApi`) にして DLL に渡す。DLL はエンジンの exe にリンクしないので、exe の名前を変えても、エディターでも書き出したゲームでも、同じ DLL が動く。表の形が変わったら版の番号 (`RM_ABI_VERSION`) を上げ、合わない DLL は読まない。境目では `std::string` や仮想関数を使わない (コンパイラや設定が違うと形が合わないため)。3D や 2D の物はプラグインがそれぞれ表を差し出す (ゲーム制作は空間を知らない)
- **MSBuild と vswhere** — Visual Studio のビルドの道具。エディターがスクリプト用の `.vcxproj` (Visual Studio のプロジェクトのファイル) を書き、MSBuild にビルドさせる。MSBuild の場所は vswhere (Visual Studio の場所を教えるツール) で探す。同じ `.vcxproj` を Visual Studio で開くと、インクルードパスが入っているので補完 (IntelliSense) が効く
- **リフレクションの生成 (スクリプト用)** — rmgen がスクリプトのヘッダーを読んで、欄の表と登録の関数を C++ で書き出し、DLL に一緒にビルドする。エンジンはその表から、インスペクター・保存・Undo を部品と同じように作る
- **SEH (構造化例外処理)** — Windows の `__try` / `__except`。スクリプトがヌルポインタを触るなどして落ちても、その呼び出しの外で捕まえて、そのスクリプトだけを止める。エディターは落ちない
- **ホットリロード** — スクリプトを書き換えて保存すると、裏でビルドし、フレームの切れ目で新しい DLL に入れ替える。値は保存と同じ仕組みで名前で書き出して読み戻す (足した欄は既定値、消した欄は残す)。Play 中は入れ替えず、止めたときに Play 前に戻してから入れ替える
- **どこ** — `plugins/rm_engine/game_production/runtime/Scripts.*`・`ScriptGuard.cpp`・`sdk/RM.h`・`sdk/RmAbi.h`、`editor/ScriptBuild.*`・`GameScripts.*`、`tools/rmgen` (`--scripts`)、3D / 2D の部分は `game_x_3d/runtime/ScriptTransform3D.*`・`game_x_2d/runtime/ScriptTransform2D.*` (テスト: `tests/TestScripts.cpp`・`TestScriptBuild.cpp`)

### Prefab (型紙と上書き)
- **何か** — エンティティ (子ごと) を 1 つのファイル (JSON) にして、何度でも置けるようにしたもの。Prefab を直すと置いた物全部に伝わる。置いた物で変えた所 (**上書き**) は残る
- **しくみ** — 置いた物の各エンティティは「Prefab のファイルの中の何番か」(`source`) を覚える。上書きは「元の Prefab との差分」: 欄ごと (エンティティ・部品の一番上の欄) に違う値、足した部品、消した部品、消した子。Prefab が変わったら、**元の Prefab と比べて上書きを取り出す → 新しい Prefab から作り直す → 上書きを掛ける**。ID は `source` で合わせて保つので、Undo や他の参照が切れない。一番上の物の名前と置き場所 (Transform) はいつも上書き (置いた場所が Prefab に引っぱられない)
- **保存** — 上書きは保存のときに作って `.rmpf` に書く。開くときは Prefab のファイル + 上書きで作り直す (Prefab を外で直していても合う)
- **ファイルの指し方** — Prefab のファイルはアセットの ID (`.meta` の GUID) で指す。動かしても名前を変えても外れない
- **入れ子** — Prefab の中に置いた Prefab は、外のファイルには「一番上の物 + 自分の Prefab へのつながり + その Prefab に対する上書き」だけを書き、中身はいつも自分のファイルから作る (Unity の Nested Prefab と同じ考え)。だから中の Prefab を直すと、どの外の Prefab の中にあっても伝わる。作るときは外から内へ順に。自分の中に自分が入る形 (輪) は作らない
- **どこ** — `plugins/rm_engine/game_production/runtime/Prefab.*` (テスト: `tests/TestPrefab.cpp`)

### ランタイムの登録 (書き出したゲームがプラグインの物を読む口)
- **何か** — プラグインが差し出す物 (システムなど) のうち、ゲームにも要る物は「ランタイムの部分」が登録する。登録の入れ物 (`RuntimeRegistry`) はゲームに入る層にあり、エディターを知らない。エディターの登録 (`PluginRegistry`) はそれを受け継ぎ、同じ入れ物にランタイムの部分 → エディターの部分の順で登録させる。だからエディターの Play と書き出したゲームが同じ一覧を見る
- **一覧** — ランタイムの部分を持つプラグインは `plugins/RuntimePlugins.cpp` に 1 行ずつ (ゲームの exe もリンクできるよう、ランタイムのヘッダーだけ。層の検査で見張る)
- **どこ** — `src/core/RuntimeRegistry.h`、`plugins/RuntimePlugins.cpp`、`plugins/rm_engine/game_x_3d/runtime/Register.cpp`

### 3D の座標変換 (行列とオイラー角)
- **何か** — 物の位置・回転・大きさを 4×4 の行列 1 つにまとめ、点に掛けると「その物の中の点が世界のどこにあるか」が出る計算。親子のときは親の行列 × 子の行列
- **決まり** — 列ベクトル (`p' = M × p`)。大きさ → 回転 → 移動 の順。回転は度で持ち、X 軸 → Y 軸 → Z 軸 の順に回す (オイラー角)
- **どこ** — `plugins/rm_engine/space3d/runtime/Transform.*` (テスト: `tests/TestSpace3d.cpp`)

### 2D の座標変換 (2D のアフィン行列)
- **何か** — 平面の物の位置・回転・大きさを 3×2 の行列 1 つ (`a b c d` = X 軸と Y 軸がどこへ行くか + `tx ty` = 原点がどこへ行くか) にまとめる。3D の 4×4 と同じ考えで、親子は親の行列 × 子の行列
- **決まり** — X が右・Y が上・反時計回りが +。画面は Y が下向きなので、カメラの行列 (`ScreenMatrix`) で上下をひっくり返す。行列式 (`ad - bc`) が負なら鏡に映っている (その下では回転が逆向きになる)
- **奥行きの代わりの「並び順」** — 2D には Z が無いので、整数の並び順で手前・奥を決める。子は親の並び順に足す。同じなら階層で後ろの物が手前 (安定ソート)
- **どこ** — `plugins/rm_engine/space2d/runtime/Transform2D.*` (テスト: `tests/TestSpace2d.cpp`)

### 2D のカメラ (マウスの下に近づく) と格子の刻み
- **マウスの下に近づく** — 近づく前に「マウスの下の平面の点」を覚え、拡大した後にもう一度求め、ずれた分だけカメラの真ん中を動かす。地図アプリのホイールと同じ動き
- **格子の刻み** — 近づくと細かく、離れると粗く。線の間が 12 DIP より狭くならない「1・2・5 × 10 の何乗」の一番小さい値を選ぶ (グラフの目盛りの決め方と同じ)
- **当たり** — クリックした点を物の逆行列で物の中の座標に戻し、四角の中かを見る (回っていても鏡でも同じ式)
- **どこ** — `plugins/rm_engine/space2d/runtime/View2D.*` (テスト: `tests/TestSpace2d.cpp`)

### Direct2D で画像を回す・色を掛ける (2D の描画)
- **何か** — UI を描いている Direct2D で、そのまま 2D のゲームの絵も描く。`SetTransform` に行列を入れて `DrawBitmap` すると、GPU が回転・拡大・反転・半透明をしてくれる
- **色を掛ける** — Direct2D の効果 (エフェクト) `ColorMatrix` に、対角に (赤, 緑, 青, 透明度) を並べた行列を入れ、画像を通して描く (`DrawImage`)。白のときは効果を使わない
- **ドット絵** — 拡大するときの混ぜ方を「一番近いピクセル」(`NEAREST_NEIGHBOR`) にすると、ピクセルが四角のまま大きくなる
- **Direct3D を使わなかった理由** — 2D のスプライトは Direct2D で十分速く、UI と同じ所に直接描ける (3D のような自分のテクスチャ・シェーダーが要らない)。数千を超えたらまとめ描き (インスタンシング) を考える
- **画像の読み込み (WIC)** — Windows の画像の部品 WIC で PNG / JPEG / BMP / GIF / TIFF を読み、32 ビット (BGRA・乗算済みアルファ) に変えて Direct2D のビットマップにする。Hub のロゴと同じ関数 (`platform::LoadBitmapFromMemory`)
- **どこ** — `plugins/rm_engine/space2d/runtime/Renderer2D.*`、`src/platform/Gfx.cpp`、`plugins/rm_engine/game_x_2d/editor/SceneView2D.cpp`

### 2D のギズモ (画面の上で決まった大きさ)
- **何か** — 選んだ物の上の矢印・輪・箱。画面の上の DIP で形を決め (近づいても同じ大きさ)、マウスとの距離 (線分までの距離・輪の半径との差) でつかむ物を決める
- **回転を何周でも数える** — 毎回「前のマウスの角度との差」を -180〜180 に直して足していく (`atan2` は ±180 で飛ぶので、そのまま引くと 1 周目で止まる)
- **どこ** — `plugins/rm_engine/space2d/editor/Gizmo2D.*` (テスト: `tests/TestSpace2d.cpp`)

### スプライトシート (アトラス) とコマ送りのアニメーション
- **アトラス** — 小さな絵をたくさん、1 枚の大きな画像に格子状に並べたもの。描くときは「何番目のコマか」から、そのコマの四角だけを切り出して描く (`DrawBitmap` の元の四角)。画像を何枚も持たずに済み、GPU の切り替えも減る
- **コマ送り** — 遊んだ時間 × 1 秒のコマ数 の整数部分を、コマの並びの数で割った余り (繰り返す) か、最後で止める。時間から毎回計算するので、フレームの速さが変わってもずれない
- **どこ** — `plugins/rm_engine/space2d/runtime/Atlas.*`、`plugins/rm_engine/game_x_2d/runtime/SpriteAnimation.*` (テスト: `tests/TestSpace2d.cpp`)

### 四角で囲んで選ぶ (ラバーバンド選択)
- **何か** — 何も無い所からドラッグして四角を作り、その中 (に触れる物) をまとめて選ぶ。物の形を画面に写して、外接の四角どうしが重なるかで決める (回っている物も同じ式)

### 一覧から選ぶ空間 (3D / 2D) を文字で合わせる

### Direct3D 11 での 3D 描画 (シェーダー)
- **何か** — GPU に 3D の形を描かせる仕組み。頂点 (点) を並べたバッファ・それを画面に置く**頂点シェーダー**・色を決める**ピクセルシェーダー**・手前の物だけを残す**深度バッファ**で描く
- **何に使っているか** — 3D 空間プラグインの描画の部分が、シーンビューの床のグリッド・軸・箱を描く
- **シェーダー** — HLSL という GPU 用の言語でコードの中に書き、最初に使うときに `D3DCompile` (Windows に入っている) で GPU 用に変換する。箱は「光の向きと面の向きの角度」で明るさを変える (ランバート反射) + 空からの明かりを少し
- **定数バッファ** — 行列や色を GPU に渡す箱。行列は「列ごと」に並べて持っていて、HLSL の決まりと同じなので、そのまま渡せる
- **MSAA (マルチサンプル アンチエイリアス)** — 1 ピクセルを 4 つに分けて描き、最後に混ぜる (`ResolveSubresource`)。線のギザギザが消える
- **どこ** — `plugins/rm_engine/space3d/runtime/Renderer3D.*`

### Direct3D と Direct2D を混ぜる
- **何か** — 3D は Direct3D、UI は Direct2D で描いているが、同じ GPU (デバイス) を使っているので、Direct3D で描いたテクスチャを Direct2D の画像 (ビットマップ) としてそのまま貼れる (`CreateBitmapFromDxgiSurface`。コピーしない)
- **工夫** — Direct2D の描きかけを先に GPU へ送り (`Flush`)、3D は別のテクスチャに描く。絵の大きさは画面のピクセル数に合わせる (高 DPI でもぼやけない)
- **どこ** — `plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp`

### 3D のカメラとクリックで選ぶ (レイ)
- **透視投影・LookAt** — 遠くの物ほど小さく見せる行列と、カメラの位置と向きから作る行列。右手系・Y が上
- **逆行列** — 行列を元に戻す行列。「画面のこの点」から「3D 空間のどの向き」かを逆にたどるのに使う
- **レイとの当たり** — クリックした点から 3D 空間へ光線 (レイ) を飛ばし、どの箱に最初に当たるかを調べる。箱は「スラブ法」(x・y・z の 3 方向の板に挟まれた区間が重なるか) で調べる。回したり大きくしたりした箱は、レイの方を箱の向きに戻してから調べる
- **編集用のカメラ** — 見ている点 (ピボット)・左右の角度・上下の角度・距離で持つ。見回す (目が動かない) / 回る (見ている点が動かない) / 平行移動 / 近づく / 飛ぶ を計算で分けている
- **どこ** — `plugins/rm_engine/space3d/runtime/View.*` (テスト: `tests/TestSpace3d.cpp`)

### 3D モデルのファイルを読む (glTF 2.0 / GLB / OBJ)
- **何か** — Blender などで作った 3D モデルの形 (頂点の位置・法線・UV と、それをつなぐ三角形) をファイルから読む
- **glTF 2.0** — Khronos が決めた「3D の JPEG」と呼ばれる形式。中身は JSON (どのバイト列が何か: `buffers` → `bufferViews` (バイト列の区切り) → `accessors` (「ここから float が 3 つずつ 100 組」) → `meshes` の `primitives` (位置・法線・UV・インデックス)) と、バイナリー (数の並び)。`.gltf` は JSON とバイナリーが別ファイル (か、バイナリーを base64 で JSON の中に埋め込む `data:` URI)、`.glb` は 1 つのファイル (12 バイトの見出し + JSON のかたまり + バイナリーのかたまり)
- **ノード** — glTF は物の置き場所を木で持つ (ノード = 行列か 位置・回転 (四元数)・大きさ)。親から子へ行列を掛けていき、頂点に焼き込んで 1 つの形にする。鏡に映す行列 (大きさがマイナス) のときは三角形の向きが裏返るので、頂点の順を入れ替えて表を保つ
- **OBJ** — 古くからある文字の形式。`v` (位置)・`vt` (UV)・`vn` (法線)・`f` (面: 頂点の番号。1 から数える、マイナスは後ろから)。多角形は扇形に三角形に切る。同じ番号の組 (v/vt/vn) は 1 つの頂点にまとめる (ハッシュ表)
- **法線を作る** — ファイルに法線が無ければ、三角形の 2 辺の外積 (長さ = 面積の 2 倍) を頂点ごとに足して長さ 1 にする (大きい面ほど強く効く、なめらかな法線)
- **外部ライブラリを使わない理由** — 要るのは形だけで、glTF は今ある自作の JSON で読める (cgltf や tinygltf を入れるほどではない)。壊れたファイルでも落ちないよう、数を読む前に「バッファーからはみ出さないか」を全部確かめる
- **どこ** — `plugins/rm_engine/space3d/runtime/Mesh.*` (純粋。テスト: `tests/TestSpace3d.cpp`)、`MeshFile.*` (ファイルを読むだけ)。サンプル: `docs/samples/models/`

### FBX を読む (ノードの木・zlib の展開)
- **何か** — Autodesk の 3D モデルの形式。Maya・3ds Max・Blender・アセットストアの多くのモデルがこれ。中身は「名前・プロパティ (数・文字・配列)・子」のノードの木で、バイナリー (よく使われる) とテキストの 2 通りの書き方がある。モデルの置き場所 (`Model`)・形 (`Geometry`)・材質 (`Material`)・絵 (`Texture` / `Video`) が別々のノードで、`Connections` の「子 → 親」の線でつながる
- **FBX SDK を使わない理由とライセンス** — Autodesk の FBX SDK は無料だが独自の許諾で、エンジンに入れて書き出したゲームと一緒に配るのに向かない (ソースも無く、Windows 用の大きな DLL)。要るのは形と色だけなので、形式を自分で読む (外部ライブラリも、そのライセンスも増えない)
- **zlib (deflate) の展開** — バイナリーの FBX は大きな配列を zlib で縮めている。zlib 自体 (zlib ライセンス) を入れる代わりに、展開する側だけ (約 200 行) を書いた: ビットを下から読む・ハフマン符号 (固定の表か、ブロックごとに書かれた表) で文字か「何バイト前から何バイト写す」かを読む・最後に Adler-32 で確かめる (RFC 1950 / 1951)
- **軸と単位** — FBX は「どの軸が上か・前か・右か」と「1 単位が何センチか」をファイルに書く (`GlobalSettings`)。それを読んで、このエンジンの Y が上・メートルに直す行列を最初に掛ける
- **模型の行列** — FBX の位置・回転・大きさは、回す順 (XYZ など 6 通り)・前後の回転・回す中心 (ピボット) を含む長い式 (`T × Roff × Rp × Rpre × R × Rpost⁻¹ × Rp⁻¹ × Soff × Sp × S × Sp⁻¹`)。親の行列を掛けて頂点に焼き込む (glTF と同じ `AppendPlaced`)
- **どこ** — `plugins/rm_engine/space3d/runtime/Fbx.*`・`Inflate.*` (純粋。テストはテストの中で小さな FBX を書いて読む)。サンプル `docs/samples/models/pyramid.fbx` (`make_fbx_sample.py`、標準ライブラリだけ)

### GPU にモデルを 1 回だけ上げる
- **何か** — 頂点とインデックスを GPU のメモリー (`ID3D11Buffer`。`IMMUTABLE` = 書いたら変えない) に 1 回だけ写して、毎フレームはそれを指して描くだけにする。同じモデルを使う物が何個あっても 1 つ
- **工夫** — シーンビューがファイルのパスごとに覚え、1 秒ごとにファイルの更新時刻を見て、変わっていたら読み直す (3D ツールから書き出し直すとすぐ映る)。しばらく使われないものは捨てる (`shared_ptr` で、最後に使う物がいなくなると GPU のメモリーも返る)
- **どこ** — `Renderer::Upload` (`plugins/rm_engine/space3d/runtime/Renderer3D.*`)、`plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp`

### 読み込みの上限 (細工したファイルから守る)
- **何か** — ファイルを読むコードは「ファイルに書いてある数」を信じて場所を作りがち。細工したファイルは、数バイトで「5000 万頂点」「同じ子を 2 回ずつ 40 段 (2^40 回)」と書ける。そこで、1 つのモデルを読む間ずっと 1 つの**予算** (`ReadBudget`: 頂点の数・メモリーのバイト数・たどった回数) を持ち、場所を作る前・ノードをたどるたびに「まだ足りる?」と聞く。足りなければ理由を付けて「読めない」にする
- **数え方** — 足し算があふれないよう「上限 - 使った分」と比べる。FBX の配列は、ファイルの中が 4 バイトの数でも、持つときは 8 バイトの double なのでそれで数える
- **取り消し** — 予算は別のスレッドからの「やめて」の印 (`std::atomic<bool>`) も見るので、聞くたびに止まれる (長い読み込みでも、外した・閉じたらすぐ終わる)
- **例外とスレッド** — 作業スレッドの関数から例外 (メモリー不足の `std::bad_alloc` など) が外へ出ると、C++ は `std::terminate` でプログラムごと終わる。だから作業スレッドの本体は `try` / `catch` で包み、失敗は「読めない」として画面に返す
- **浮動小数点から整数へ** — NaN や表せないほど大きな数を `static_cast` で整数にするのは未定義の動き (何が起きてもよい)。ファイルから来た数は、double のまま範囲を確かめてから変換する
- **どこ** — `plugins/rm_engine/space3d/runtime/Mesh.*` (`ReadBudget` と上限の定数)、`Fbx.cpp`、`MeshFile.cpp`、`MeshLoader.cpp`。テストは `tests/TestSpace3d.cpp` の `Crafted_*` (細工したファイルで、落ちない・すぐ「読めない」になる)

### どのスレッドからでも書けるログ (受け手の待ち行列と、呼び出し中を待つ外し方)
- **何か** — 作業スレッド (モデル・サムネイルを読む) もログを出す。ログの受け手のうち、ファイルやデバッガーへの書き出しはどのスレッドからでもよい (自分で鍵を掛ける) が、画面を描き直す受け手は UI のスレッドでしか窓を触れない。そこで受け手を 2 種類に分け、UI の受け手には**待ち行列**に積んでおき、UI のスレッドがメッセージを 1 つ処理するたびに取り出して渡す。別のスレッドが積んだら `PostThreadMessage(WM_NULL)` で UI のスレッドを起こす
- **外すときに待つ** — 受け手はログの鍵の外で呼ぶ (受け手がまたログを書いても止まらないように)。すると「別のスレッドが受け手を呼んでいる最中に、持ち主がそれを外して消える」すき間ができる。受け手ごとに「いま呼んでいるスレッド」を覚えておき、外す人は `std::condition_variable` でそれが無くなるまで待つ。自分のスレッドが呼んでいる最中 (受け手が自分を外す) は待たない (待つと永久に止まる)
- **どこ** — `src/base/Log.*`、`src/editor/app/App.cpp` (メッセージループ)、`src/editor/shell/EditorScreen.cpp` (テスト: `tests/TestLog.cpp`)

### ファイル名がぶつからないようにハッシュを足す
- **何か** — rmgen はヘッダー 1 枚ごとに 1 つの .cpp を作る。パスの '/' を '_' にするだけだと、違うパスが同じ名前になることがある (`a/b_c/D.h` と `a/b/c/D.h`)。読める名前の後ろにパス全体のハッシュ (FNV-1a) を付けると、違うパスはまず違う名前になる。それでも万一同じになったら (Windows は大文字小文字を区別しないので、それも含めて比べる) エラーで止める: 黙って 1 つを上書きしない
- **どこ** — `tools/rmgen/Scanner.cpp` (`OutputName` と `Validate`。テスト: `tests/TestRmgen.cpp`)

### モデルを別のスレッドで読む (作業スレッドと待ち行列)
- **何か** — 大きなモデルのファイルを読んで解くのは時間がかかる (数十 MB で 1 秒以上)。描くのと同じスレッドで読むと、その間画面が止まる。そこで、読むだけの**作業スレッド**を 1 本作り、「このファイルを読んで」を**待ち行列** (`std::deque`) に積んでおくと、順に読んで結果を置いておく。描く側は毎フレーム「終わった?」と聞き (`Take`)、終わっていれば受け取る
- **std::jthread と stop_token** — C++20 のスレッド。壊すときに自動で「止まって」と頼み (`request_stop`) 終わりを待つ (`join`)。待ち行列が空の間は `std::condition_variable_any` で眠り、頼まれるか止めるように言われると起きる
- **mutex** — 待ち行列と結果の表は 2 つのスレッドが触るので、`std::mutex` で 1 度に 1 つずつ。読んでいる間 (時間のかかる所) は鍵を外す
- **GPU は描くスレッドだけ** — Direct3D 11 の描く道具 (デバイスコンテキスト) と WIC の画像の道具は、別のスレッドから同時に使うと壊れる。作業スレッドがするのは「ファイル → 頂点と三角形」(純粋な計算) だけにして、GPU に上げるのと絵を解くのは受け取った描くスレッドでする
- **やめる** — 外した・別のモデルに変えたものは `Cancel`: まだなら読まない、読んでいる最中なら終わった結果を捨てる
- **どこ** — `plugins/rm_engine/space3d/runtime/MeshLoader.*` (テスト: `tests/TestSpace3d.cpp`。読む関数を差し替えて、順番・やめる・壊すときを確かめる)、使う所は `plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp`

### 影 (シャドウマップと PCF)
- **シャドウマップ** — まず光の位置から見た「一番手前の物までの深さ」だけの絵 (深度テクスチャ) を描く。次に普通に描くとき、各ピクセルが「光から見た自分の深さ」とその絵の深さを比べ、絵の方が手前なら間に何かある = 影
- **平行光と正射影** — 太陽のような平行な光なので、光から見る行列は遠近の無い正射影。影を落とす物全部を囲む箱が、ちょうどその正射影に収まるように作る (物が動かない限り変わらないので、カメラを動かしても影がちらつかない)
- **PCF (Percentage Closer Filtering)** — 1 か所だけで比べると影の縁がギザギザになるので、周りの 3 × 3 か所で比べて「何割が影か」を明るさにする。GPU の**比較サンプラー** (`SamplerComparisonState` + `SampleCmpLevelZero`) は 1 回で 2 × 2 の比べた結果を混ぜてくれるので、さらになめらか
- **影のにきび (shadow acne) を防ぐ** — 面が自分自身の影になって縞模様が出るのを、深さを少しずらす (傾きに比例したずれ `SlopeScaledDepthBias` + テクセル 1 つ分) のと、法線の向きに少しずらした所で比べる (normal offset) ので防ぐ
- **1 枚のテクスチャを 2 通りに見る** — `R32_TYPELESS` で作り、書くときは深度 (`D32_FLOAT` の DSV)、読むときは数 (`R32_FLOAT` の SRV) として使う
- **床の影** — Y = 0 に見えない大きな板を置き、影の所だけ半透明の色を重ねる (深度は書かないので、グリッドの線はその上に乗る)
- **どこ** — `plugins/rm_engine/space3d/runtime/Renderer3D.*` (HLSL も中)、光の行列は `View.*` の `DirectionalShadowMatrix` (純粋。テストあり)

### 影をいくつもの光から (カスケード・点光源・スポット)
- **カスケード シャドウマップ** — 広い場所を 1 枚の影の地図に収めると、1 テクセルが大きくなって影がぼやける。そこでカメラの前を近い所・中くらい・遠い所の 3 つに分け、それぞれに地図を 1 枚ずつ作る (近くの地図ほど狭い範囲 = くっきり)。分け方は「等比 (近いほど細かく)」と「等間隔」を混ぜたもの (practical split)
- **ちらつかないように** — 地図を各部分を**囲む球**に合わせる (カメラが回っても大きさが変わらない) のと、地図の真ん中を**テクセル単位に切り捨てて動かす** (カメラが少し動いても、影の縁のテクセルの並びがずれない)
- **点光源の影** — 光から 6 方向 (立方体の面) を 90 度より少し広い透視で描く。どの地図を見るかは「光から見た向きの x・y・z のどれが一番大きいか」で決める (キューブマップと同じ考え方を、普通の地図 6 枚で)
- **スポットの影** — 円すいを囲む透視の地図 1 枚
- **透視の地図の深度のずれ** — 透視では奥ほど深さの値が詰まるので、決まった量ずらすと遠くでずれすぎる / 近くで足りない。「テクセル 1 つ分の世界の長さ」を深さの式の微分で地図の深さに直し、距離で割ってずらす
- **アトラス (タイルに並べる)** — 地図を 1 枚の大きなテクスチャに並べ、描くときはビューポートでタイルを選び、読むときは uv をタイルの場所に直す。テクスチャの配列を比較サンプラーで読むのはシェーダーモデル 4.1 から (Direct3D 10.1 の GPU) なので、10.0 の GPU でも動くようにこうした
- **どこ** — `plugins/rm_engine/space3d/runtime/Lighting.*` (地図の行列・分け方。純粋。テスト: `tests/TestSpace3d.cpp`)、`Renderer3D.cpp` (描くのと HLSL)

### カメラの部品 (透視投影と平行投影・視錐台)
- **透視投影と平行投影** — 透視は遠くの物ほど小さく (目と同じ。画角 = 縦に見える角度)。平行投影 (正射影) は遠くても同じ大きさ (図面・2D 風のゲーム。「見える大きさ」= 画面の縦の半分の長さ)。どちらも「見える箱」を -1〜1 × -1〜1 × 奥行き 0〜1 に写す 4 × 4 の行列
- **カメラの行列は置き場所の逆** — カメラを置いた行列 (ワールド行列) から「目の位置・見る向き (-Z)・上 (+Y)」を取り出して `LookAt` で作る。逆行列をそのまま使わないのは、大きさが入っていると絵がゆがむから
- **視錐台 (見える範囲の形)** — view-projection の**逆行列**に画面の四隅 (-1/1) と奥行き 0 / 1 を掛けると、近い面と遠い面の 8 つの角が世界のどこにあるかが出る。それを線で結んでシーンビューに描く (透視なら四角すい台、平行投影なら箱)
- **どこ** — `plugins/rm_engine/game_x_3d/runtime/Camera.*`・`plugins/rm_engine/space3d/runtime/View.*` の `ViewFromWorld` / `FrustumCorners` (純粋。テスト: `tests/TestSpace3d.cpp`)、描くのは `SceneView3D.cpp`

### いくつもの光 (平行光・点光源・スポット)
- **3 つの光** — 平行光 = 太陽 (どこでも同じ向き)。点光源 = 電球 (場所から周りへ。遠いほど弱い)。スポット = 懐中電灯 (向きのまわりの円すいの中だけ)。どれも「面の向きと光の来る向きの角度の cos」(ランバート反射) × 色 × 強さ を足し合わせる
- **弱まり** — 点光源・スポットは「届く距離」で 0 になるよう (1 − 距離 / 届く距離)² で弱める (なめらかに 0 へ。物理の 1/距離² だと 0 にならず、遠くの物まで全部計算することになる)。スポットの縁は `smoothstep` で、円すいの縁から半角の 3/4 までなめらかにぼかす (cos の値どうしで比べるので、角度に戻す計算が要らない)
- **定数バッファの配列** — 光を 8 個までの配列 (位置・向き・色・円すいの cos を `float4` ずつ) にして 1 フレームに 1 回 GPU に送り (`register(b1)`)、ピクセルシェーダーが光の数だけループで足す。CPU 側で値を詰める所 (`MakeLights`) は純粋な関数にしてテストする (色 × 強さ・向きを長さ 1 に・cos・影の光の選び方)
- **影** — 平行光は影を落とすものの 1 つ目だけ。点光源とスポットは影の地図 8 枚を分け合う (下の「影をいくつもの光から」)
- **環境光 (半球ライティング)** — どの面にも当たる光を、上からの色 (空) と下からの色 (地面) の 2 色にして、面の向きで混ぜる。1 色より、物の上と下で色が違って立体に見える
- **どこ** — `plugins/rm_engine/space3d/runtime/Lighting.*` (純粋。テストあり)、HLSL の `Shade` / `LightAt` / `ShadowOf` は `Renderer3D.cpp`、部品は `plugins/rm_engine/game_x_3d/runtime/Light.*`

### 視錐台カリング (カメラの外の物を描かない)
- **何か** — カメラに見える範囲 (視錐台: 近い面・遠い面・上下左右の 6 枚の面で囲まれた形) の完全に外にある物は、GPU に描かせない。描いても画面に出ないので見た目は同じで、物が多いときに速くなる
- **やり方** — 物を囲む箱 (ワールドの軸にそろえた箱) の 8 つの角に view-projection の行列を掛けて**クリップ空間** (割り算の前の x, y, z, w) にする。そこでは 6 枚の面が `x < -w`・`x > w`・`y < -w`・`y > w`・`z < 0`・`z > w` という簡単な式になる。8 つの角が**全部同じ面の外**なら見えない (角ごとに「どの面の外か」を 6 ビットで持ち、全部の AND が 0 でなければ外)。割り算をしないので、目の後ろの角があっても正しい
- **影との関係** — カメラの外の物も、影は画面の中に落ちることがある。だから影の絵 (シャドウマップ) には外の物も描き、外すのは普通の絵だけ
- **どこ** — `plugins/rm_engine/space3d/runtime/View.*` の `BoxInView` (純粋。テスト: `tests/TestSpace3d.cpp`)、使うのは `Renderer3D.cpp`

### 1 フレームの数をまとめて送る (インスタンスの番号で選ぶ)
- **何か** — GPU に描かせるたびに CPU から数 (行列や色) を送ると、送る回数 (API の呼び出し) が物の数 × 影の地図の数だけ増えて、CPU が重くなる。そこで**全部の物と材質の数を 1 つのバッファにまとめて、フレームの最初に 1 回だけ送る**。描く命令は「何番目の物の数を使うか」だけを伝える
- **番号の伝え方** — 「インスタンスごとの頂点の流れ」(per-instance の頂点バッファ) に番号の組を並べ、描く命令の「始めのインスタンス」(`StartInstanceLocation`) でどの組を読むかを選ぶ。シェーダーはその番号でバッファ (`Buffer<float4>` の `Load`) から行列や色を読む。Direct3D 10.0 の GPU でも使える方法 (構造化バッファや定数バッファの一部を指す方法は 11 から)
- **どこ** — `plugins/rm_engine/space3d/runtime/Renderer3D.cpp` (`AddThing` / `AddMaterial` / `AddDraw` / `UploadFrame`、HLSL の `LoadPlace` / `LoadLook`)

### インスタンシング (同じ形を 1 回の命令でたくさん描く)
- **何か** — 同じメッシュを何個も描くとき、1 個ずつ「描いて」と頼む代わりに「このメッシュを N 個」と 1 回で頼む (`DrawIndexedInstanced` のインスタンスの数)。GPU は 1 個ずつ番号 (`SV_InstanceID` / インスタンスごとの頂点の流れ) を変えながら描くので、置き場所や色は番号で別々にできる。CPU が API を呼ぶ回数が物の数から「種類の数」に減る
- **まとめられる条件** — 同じメッシュ・同じ部分・同じ絵 (テクスチャを替えるには命令の間で GPU の設定を変える必要がある)。材質の数 (色・金属・ざらざら) は物ごとのバッファから読むので、違っていてもまとめられる
- **どこ** — `Renderer3D.cpp` の `Emit` (前の命令に続けられるならインスタンスを足す)

### 描く順の並べ替え (状態の切り替えを減らす)
- **何か** — GPU の設定 (シェーダー・テクスチャ・頂点のバッファ) を替えるのは、描くこと自体より CPU に重い。そこで描く前に「シェーダー → 絵 → メッシュ」の順に並べると、同じ設定の命令が続き、切り替えもインスタンシングでまとめられる所も増える
- **安定した並べ替え** — 同じ鍵の物は来た順のまま (`std::stable_sort`)。もう並んでいれば並べ替えない (`std::is_sorted` を先に見る)。透ける物は「奥から順」が絵に要るので並べ替えない
- **絵が変わらない理由** — 透けない物は深度のテストで手前が残る (深さが全く同じ所だけ順で決まる)。影の地図は一番近い深さが残るだけなので、順に関係なく同じ
- **どこ** — `plugins/rm_engine/space3d/runtime/DrawOrder.*` (純粋。テスト: `tests/TestSpace3d.cpp`)

### 見える範囲を平面で調べる (視錐台の 6 面)
- **何か** — 「箱が見える範囲に入るか」を、箱の 8 つの角を全部行列に通して調べる代わりに、見える範囲の 6 つの面を平面の式 (ax + by + cz + d ≥ 0 が内側) にしておき、面ごとに**箱の一番内側の角**だけを調べる (その角が外なら、全部の角が外)。平面は投影の行列の行を足し引きするだけで出る (Gribb と Hartmann の方法)。1 つの見え方で何千個も調べるときに速い
- **どこ** — `View.h` の `Frustum` / `FrustumOf` / `BoxInFrustum` (テストで、角を全部通す `BoxInView` と答えが同じことを確かめた)

### 止まっている物の影の層 (深さを写して、動く物だけ描き足す)
- **何か** — 1 つの物が動くと、その物が入る影の地図は描き直しになる。地図の中の止まっている物まで毎回描くのは無駄なので、**止まっている物だけの深さの絵 (層)** を別に取っておき、地図には層をそのまま写してから、動く物だけを描き足す
- **深さを写す** — 深さのテクスチャは、テクスチャの一部だけを写す命令 (`CopySubresourceRegion`) が使えない (深さの物は丸ごとだけ)。そこで全面の三角形を描き、ピクセルシェーダーが層の深さを読んでそのまま深さとして出す (`SV_Depth`)。機能レベル 10.0 で使える
- **絵が変わらない理由** — 影の地図は「一番近い深さ」が残るだけなので、層 + 動く物と、全部を一度に描いたものは同じになる
- **どこ** — `Renderer3D.cpp` (`CopyDepthPS`・`Shared::EnsureLayer`・`planMap`)。動いているかはシーンビューが決める (`SceneView3D.cpp` の `NoteMotion`: この 1 秒に置き場所が変わった物)

### 影の地図を描き直さない (指紋)
- **何か** — 影の地図は「光の位置から見た深さの絵」なので、光も影を落とす物も動かなければ前のフレームと同じ。そこで地図ごとに**中身の指紋** (光の行列と、中に描く物の形の番号と置き場所の行列から作る 64 ビットのハッシュ) を覚え、同じなら描かない (物ごとの指紋はフレームに 1 回作り、4 バイトずつ混ぜる)
- **共有** — シェーダー・影の地図は GPU (デバイス) ごとに 1 つにして、シーンビュー・プレビュー・サムネイルの描き手で分け合う (`std::weak_ptr` の表。最後の描き手が消えると消える)。地図の指紋も一緒に持つので、ほかの描き手が描いた地図もそのまま使える
- **測り方** — `tools/bench3d` (箱 1000 個・光 8 個で `Render` の CPU の時間を測る小さな exe。GPU の終わりはフレームの間で待って時間に入れない)
- **どこ** — `Renderer3D.cpp` (`Renderer::Shared`・`planMap`)

### 1 フレームに 3D の絵を 2 枚 (プレビュー)
- Direct2D は描く命令をためておき、後でまとめて GPU に送る。だから 1 枚目の 3D の絵を貼る命令がまだ残っているうちに、同じテクスチャへ 2 枚目を描くと 1 枚目が消える。プレビューは**別の描き手 (`Renderer`) と別のテクスチャ**に描く。モデルの形 (頂点のバッファ) は同じ GPU なので 2 つの描き手で共有できる
- **どこ** — `plugins/rm_engine/game_x_3d/editor/SceneView3D.cpp` (`Picture`)

### 材質とテクスチャ (モデルの色と絵)
- **何か** — モデルの面の色。glTF では**材質** (`materials`) の `pbrMetallicRoughness.baseColorFactor` (色) と `baseColorTexture` (絵)、OBJ では横の `.mtl` ファイルの `Kd` (色) と `map_Kd` (絵)。面の各頂点の **UV** (絵の中のどこか。0〜1、はみ出すとくり返す) で絵を貼る
- **サブメッシュ** — 1 つのモデルに材質がいくつもあるので、三角形を材質ごとに並べ替え、「何番目から何個の三角形は材質 2」という部分 (`MeshPart`) にする。GPU には 1 回で全部載せ、描くときは部分ごとに材質を替えて `DrawIndexed(個数, 始まり)` するだけ (並べ替えはカウントして置き直す: 材質の数に関係なく 2 回なめるだけ)
- **色の計算** — 色 = 材質の色 × 絵の色 × 光の量。シェーダーの `Paint()` が「表面の色」を出し、光の計算はその後で掛けるだけ (光の作り方と分けてある)
- **リニアと sRGB** — 画面の数字 (sRGB) は人の目に合わせて曲げてあり、0.5 は「光の量の半分」ではない。光を足したり掛けたりするのは光の量 (リニア) でないと正しくないので、色はリニアで持ち、計算もリニアで、最後に画面の数字に直す (下の「PBR」)。色の絵は `_SRGB` の形式で GPU に置くと、読むときに GPU がリニアに直してくれる
- **ミップマップ** — 絵を半分・4 分の 1 … と小さくした組を一緒に GPU に持たせ、遠くの (画面で小さい) 面は小さい絵から色を取る。遠くで縞がちらちらする (モアレ) のを防ぐ。CPU で 2 × 2 の平均を取って作り、`IMMUTABLE` のテクスチャに全部の段を最初から入れる。サンプラーは異方性フィルター (斜めに見た面もぼけにくい) とくり返し (`WRAP`)
- **アルファの 3 つの扱い** (glTF の `alphaMode`) — OPAQUE (絵の透明度は見ない)・MASK (ある値より透けている所は描かない = 切り抜き。HLSL の `clip`)・BLEND (半分透ける。下の「透ける物を奥から順に」)
- **選んだ物を色を変えずに見せる** — 面が目の方を向いていない所ほど (面の向き・目への向きの内積が 0 に近いほど) アクセントの色を混ぜる (リムライト / フレネル風)。輪郭だけが光る
- **重い所は別のスレッドで** — 絵を解く (WIC) のとミップマップを作る (CPU) のは作業スレッド (`PictureDecoder`)、GPU に写すだけが描くスレッド。写すのも 1 フレームに 32 MB まで (1 枚目はいつも) にして、残りは次のフレームへ。絵は `shared_ptr` で持ち合い (参照カウント)、使う物がいる間は消えない。作った描き手の番号 (`madeBy`) を覚え、GPU が作り直された後の古い絵は使わない。結果は `shared_ptr` で頼んだ側と共有し、`atomic<bool>` の「できた」を立ててから渡す (release / acquire: 立つ前に書いた中身が、立ったのを見た側から必ず見える)。sRGB とリニアの直しは 256 と 4096 の表で (ピクセルごとの `pow` をやめて速く)
- **キャッシュ** — 絵のファイルはフルパスごとに 1 回だけ GPU に上げ、何個のモデルが使っても 1 つ。1 秒ごとにファイルの時刻を見て、ペイントで描き直したら読み直す (取り込みの設定を変えて `.meta` が新しくなったときも)
- **くっきり (点のサンプリング)** — 絵から色を取るとき、近くの 4 つの点を混ぜる (なめらか) 代わりに一番近い 1 点だけを取る (`D3D11_FILTER_MIN_MAG_POINT_MIP_LINEAR`)。ドット絵を拡大してもぼけない。画像の取り込みの設定で選び、描くときに材質ごとにサンプラーを替える
- **どこ** — 読む: `plugins/rm_engine/space3d/runtime/Mesh.*` (純粋。テスト: `tests/TestSpace3d.cpp`)、GPU と貼り方: `Renderer3D.*`、絵のキャッシュとモデルの材質: `Texture.*`。サンプル: `docs/samples/models/` (`make_samples.py` が PNG も標準ライブラリだけで作る: zlib で縮めた行 + PNG のかたまり)

### 透ける物を奥から順に描く
- **なぜ** — 透ける色は「後ろにある色」に混ぜて描く。だから後ろの物が先に描かれていないと混ざらない。不透明な物は深度バッファがどれが手前か決めてくれるので順番は要らないが、透ける物は**遠い順** (画家のアルゴリズム) に描く
- **やり方** — 不透明な物を全部描いた後で、透ける部分を「目から部分の真ん中までの距離」の遠い順に並べて描く。そのとき深度は**読むが書かない** (不透明な物の後ろは隠れ、透ける物どうしは重ねて見える)
- **限界** — 部分の中の三角形の順は変えないので、1 つの部分が自分と重なる (ねじれたリボンなど) と前後が逆に見える所がある。完全に解くには三角形ごとの並べ替えか、順番の要らない透明 (OIT) が要る
- **どこ** — `BackToFront` (`plugins/rm_engine/space3d/runtime/View.*`。テストあり)、描く順は `Renderer3D.cpp` の `Render`

### PBR (金属・ざらざら) と法線マップ
- **何か** — 物理に基づく描き方 (Physically Based Rendering)。材質を「色」「金属か (metallic)」「ざらざら (roughness)」で表し、光の当たり方を物理に近い式で計算する。Unity・Unreal・Blender・glTF が同じ考え方なので、そこで作った材質がそのまま同じように見える
- **2 つの光り方** — 拡散 (面の中に入って色が付いて出てくる光。Lambert = 光と面の角度の cos) と、つや (表面で鏡のように跳ね返る光)。金属は拡散が無く、つやに自分の色が付く。金属でない物のつやは白くて弱い (正面から 4%)
- **つやの式 (Cook-Torrance)** — D × G × F ÷ (4 × cos × cos)。**D** (GGX) = 小さな面のうち、光と目のちょうど真ん中を向いている物の割合 (ざらざらほど広く低く)。**G** (Smith) = 小さな面どうしで隠れて届かない分を引く。**F** (Schlick) = 斜めから見るほど鏡に近くなる (水面と同じ)。ざらざら = 光の点が大きくぼやけ、つるつる = 小さく鋭い
- **空** — 環境マップ (周りの景色の絵) はまだ無いので、上が明るく下が暗い空を、拡散と映り込みに少しずつ足すだけ
- **法線マップ** — 形はそのままで、ピクセルごとに面の向きを絵 (RGB = 向きの XYZ) で曲げ、細かい凹凸に見せる。絵の向きを世界の向きに直すには面の「接線」(U と V の向き) が要るが、頂点に持たせずに、**画面の上で隣のピクセルとの位置と UV の差 (`ddx` / `ddy`) から作る** (cotangent frame。頂点の形を変えなくてよい)
- **光る色 (emission)** — 光の計算の後に足す。光が当たっていなくても明るい
- **どこ** — HLSL の `Shade` / `Bend` / `Paint` (`plugins/rm_engine/space3d/runtime/Renderer3D.cpp`)、読むのは `Mesh.*` (テスト: `tests/TestSpace3d.cpp`)。サンプル: `docs/samples/models/pbr_ball.glb`

### テクスチャの圧縮 (BC1 / BC3 / BC4 / BC5 / BC7) と DDS のキャッシュ
- **何か** — GPU がそのまま読める圧縮 (Block Compression)。4 × 4 の texel を 8 か 16 バイトにまとめる (RGBA なら 64 バイト)。GPU は描くときにその場で戻すので、メモリーも、GPU へ写す時間も 4〜8 分の 1
- **しくみ** — 1 つのブロックに「2 つの端の色 (か値)」と「各 texel が 2 つの間のどこか (2〜4 ビットの番号)」を持つ。BC1 = 色 2 つ (5・6・5 ビット) と 4 段、BC4 = 値 2 つと 8 段 (1 チャンネル)、BC5 = BC4 を 2 つ (ノーマルマップの x と y)、BC3 = BC1 の色 + BC4 の透明、BC7 = いくつもの「モード」から選べて細かい
- **作り方 (自作)** — 端は「16 個の色のばらつきが一番大きい向き」(共分散行列の主軸をべき乗法で) に沿って一番外の 2 つを取り、少し内側に寄せる。番号を決めた後、その番号で一番よく合う端を最小二乗法で求め直す。BC7 はモード 6 だけ (RGBA を 1 本の線と 16 段: 透明のある色に向く)
- **ライブラリを使わなかった理由** — BC7 は DirectXTex か bc7enc (どちらも MIT 系で使える) を入れるつもりだった。bc7enc (1 つの C ファイル) を取ってきたが、外から取ってきたコードをビルドに入れることが作業の権限で止められたので、自作のモード 6 にした。画質はモード 1〜3 も使うものより少し落ちる (色が細かく混ざるブロック)。入れるなら `EncodeBC7` だけを差し替えればよい
- **形式の選び方** — 使い方で決める: 色 (sRGB) は不透明なら BC1、透明があれば BC7 (BC7 は機能レベル 11.0 が要るので、10.x の GPU では BC3)。ノーマルマップは BC5 (z はシェーダーが `sqrt(1 − x² − y²)` で作る)。灰色の数は BC4 (シェーダーが .r を全部に)。上の段が 4 の倍数でない絵は圧縮しない
- **DDS のキャッシュ** — 圧縮は重い (4K の BC7 で数秒) ので、結果を DDS (Direct3D の道具が使う GPU の絵のファイル: 見出し + DX10 の見出し (DXGI の形式) + 段ごとのブロック) にして `<プロジェクト>/Cache/Textures/` に置く。名前は「何から作ったか」全部 (アセットの ID・元のバイト列のハッシュ・取り込みの設定・使い方・BC7 の有無・版) のハッシュ。どれかが変われば別の名前なので、消す・古いのを見分ける手間が要らない (Unity の Library と同じ考え: 消しても作り直す)
- **ハッシュ (FNV-1a 64)** — バイトを 1 つずつ XOR して素数を掛けるだけの速いハッシュ。暗号には使えないが「変わったか」を見るには十分
- **どこ** — `plugins/rm_engine/space3d/runtime/BlockCompress.*`・`TextureFile.*`・`Texture.cpp` (`PictureDecoder::Make`) (テスト: `tests/TestSpace3d.cpp`)

### 1 フレームに GPU へ写す時間の上限 (タイムスライス)
- **何か** — 1 フレームで GPU に絵を写すのに使ってよい時間を 2 ms に決め、越えたら残りは次のフレームへ回す (Unity の asyncUploadTimeSlice)。量 (バイト) でなく時間で区切るので、GPU や形式の違いがそのまま効く
- **測り方** — QueryPerformanceCounter (Windows の高分解能のカウンター。`platform::NowSeconds`) で写す前後を測って足す。フレームの 1 枚目はいつも写す (どんなに大きくても止まらない)。数え方は `UploadSlice` (純粋・テストあり)
- **どこ** — `plugins/rm_engine/space3d/runtime/UploadSlice.h`、`kUploadSecondsPerFrame` (`Texture.h`)

### サムネイル (GPU で描いて読み戻す・差し出しの口)
- **何か** — アセットのパネルに出す小さな絵。画像は WIC で縮めるだけ。3D モデルは**画面に出さない絵 (オフスクリーン)** に描いて、その絵を CPU に持ってくる
- **GPU から読み戻す** — GPU の絵は CPU から直接読めないので、CPU が読める写し (`D3D11_USAGE_STAGING` のテクスチャ) へ `CopyResource` し、`Map` で中を見る。1 行の長さ (`RowPitch`) は幅 × 4 より長いことがあるので、行ごとに写す
- **透けたまわり** — 透明 (0, 0, 0, 0) で消してから描くと、まわりは透明、縁は MSAA で混ざって半分透明の「事前乗算」の絵になる。そのまま Direct2D に渡せる
- **核は 3D を知らない** — 核は「この種類のファイルの小さな絵を描ける人」を差し出しの口 (`core.thumbnail` に `ThumbnailMaker`) で探すだけ。3D モデルの描き方は 3D 空間プラグインが差し出す。ほかの種類 (音の波形・フォントの見本 …) も、プラグインが同じ口に出せば出る
- **スレッドの中の例外** — `std::thread` / `std::jthread` の関数から例外が外へ出ると `std::terminate` でプログラムごと終わる。だから作業スレッドでは 1 つの仕事を `try` で包み、`std::bad_alloc` (壊れたファイルが巨大な数を書いていた) もほかの例外も「この物は作れない」という結果にして返す
- **重くしない** — ファイルを読む・絵を解く (重い所) は**作業スレッド** 1 本で (`std::jthread` + `mutex` + `condition_variable_any`。止めるときは stop_token で起こして待つ)。待ち行列は新しい順 (スクロールした先がすぐ出る)。GPU で描く所だけは UI のスレッドで、1 回の描画で 30 ミリ秒まで (Direct3D の即時コンテキストは 1 つのスレッドからしか触れない)。WIC はスレッドごとに自分の工場 (`CoInitializeEx` + `thread_local`) を持つ。32 / 64 / 128 / 256 ピクセルの段で作り、少し大きくしただけでは作り直さない。1 分見えなかったら捨てる
- **どこ** — `src/editor/assets/Thumbnails.*`、`plugins/rm_engine/space3d/editor/Thumbnail.*`、木の行の高さと絵: `src/editor/tree/TreeView.h` (`RowHeight` / `DrawPicture`)、つまみ: `w::Slider`

### ドラッグを画面の端で止めない (マウスの固定)
- **何か** — カメラを回すドラッグの間、カーソルを隠して、動くたびに**ドラッグを始めた点へ戻す** (`SetCursorPos`)。戻す前に「どれだけ動いたか」を数えるので、マウスを動かした分だけいくらでも回せる。ゲームの「マウスでの視点操作」や Unity / Blender の見回しと同じやり方
- **工夫** — 戻したときに Windows が出す「マウスが動いた」の知らせは、ちょうど始めた点なので「動いた量 0」になり、二重に数えない。ボタンを離すとカーソルが元の場所に出てくる
- **どこ** — `src/editor/app/ScreenWindow.cpp` (`MouseMoved` / `UpdateMouseLock`)、`src/ui/Context.h` (`LockMouse`)

### 押し続けるキーと、描き続けるフレーム
- このエンジンは何も起きていないときは描かない (CPU を使わない)。カメラで飛ぶときは「キーを押している間ずっと動く」必要があるので、**キーが押されているか** (`WM_KEYDOWN` / `WM_KEYUP` で覚える) と、**頼まれている間は次のフレームをすぐ描く** (`RequestAnimation`) を足した。キーを離せばまた止まる
- **どこ** — `src/ui/Context.h`、`src/editor/app/ScreenWindow.cpp`
